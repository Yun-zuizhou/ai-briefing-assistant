## 1. 当前阶段判断

当前 LLM 接入已经不是“能不能调用模型”的问题，而是进入“用户是否感知稳定、核心产品链路是否闭合、系统是否可控运行”的阶段。

已完成的主干能力：

1. API Key 服务端加密存储与历史明文清理。
2. DeepSeek provider 接入，支持 `deepseek-v4-flash` 与年报场景 `deepseek-v4-pro`。
3. Chat 对话页 LLM 意图判断、自然回复、上下文使用与失败回退。
4. 内容咨询和摘要相关 LLM 调用基础。
5. 个人画像生成、证据引用、画像文本和关键词。
6. 周报、月报、年报 LLM 文本块，含证据引用、失败回退和年报结构化输出稳定性处理。
7. `llm_invocations` 调用日志表、统计接口和开发诊断页入口。

当前阶段可定义为：

> P7 LLM 产品化与运维化阶段。

P7 不优先继续扩模型能力，而是优先收口三件事：

1. 用户侧 AI 状态统一。
2. 今日简报和信息源整理的正式 LLM 生成链路。
3. 成本、限流、重试、失败提示和诊断体验的工程治理。

---

## 2. P7 总目标

P7 的目标不是让更多页面“接上 LLM”，而是让已经接入的 LLM 能以产品可见、状态一致、失败可解释、成本可观测的方式运行。

完成后应达到：

1. 用户知道当前内容是 AI 生成、规则回退、生成中、失败还是可重新生成。
2. 今日简报不再只停留在结构化聚合，而是形成正式的 LLM 摘要、主题归并、来源引用和推荐理由。
3. 信息源整理进入 LLM 主流程的可控子路径，先做去重、归并、解释和推荐理由，不让 LLM 接管全部排序。
4. 调用成本、失败率、模型分布、耗时、失败样本能在诊断页被查看。
5. 对用户可见链路具备统一失败提示和重新生成入口。

## 3. 工作包拆分

### P7-A 用户侧 AI 状态统一

目标：

把报告、画像、简报、Chat 回复、内容咨询中分散的 AI 状态收成统一产品口径。

状态枚举建议：

| 状态 | 含义 | 用户可见文案方向 | 可操作项 |
|---|---|---|---|
| `idle` | 尚未触发生成 | 暂无 AI 内容 | 生成 |
| `generating` | 正在生成 | 正在生成 | 不允许重复点击或进入排队提示 |
| `success` | AI 成功生成 | 已生成 AI 解读 | 查看依据、重新生成 |
| `fallback` | AI 失败后规则回退 | 当前为规则结果 | 重新生成、查看失败提示 |
| `failed` | 无可展示结果 | 生成失败 | 重试 |
| `stale` | 已有结果但事实已变化 | 内容可能不是最新 | 重新生成 |

执行步骤：

1. 盘点现有状态字段：
   - `reports.generation_source`
   - `reports.provider_name`
   - `reports.model_name`
   - `reports.evidence_refs_json`
   - `user_profiles` 画像字段
   - `briefings.status`
   - `summary_generation_tasks.status`
   - `summary_generation_results`
   - `llm_invocations.status`
2. 在前端定义统一展示组件或轻量映射函数，先不强行改后端表结构。
3. 报告页先复用当前 `generationSource` 和 `llmBlocks` 判断状态。
4. 画像页、简报页补齐同一套文案。
5. 统一“重新生成”按钮的 loading、禁用、失败提示和成功刷新行为。

验收标准：

1. 周报、月报、年报、画像、今日简报至少使用同一套状态文案。
2. `fallback` 与 `success` 在用户侧能明确区分。
3. 重新生成入口不会重复提交并发请求。
4. 历史报告只读时不出现可重新生成入口。

边界：

1. 不在本步骤重构全部后端生成表。
2. 不把开发诊断页状态直接暴露给普通用户。
3. 不改变 P4 页面迁移主线的页面结构，只补状态承载点。

### P7-B 今日简报 LLM 正式生成链路

目标：

把已有 consult/summary 能力收口到今日简报与历史简报展示，使“今日信息”成为正式可读、可追溯、可回退的 LLM 生成结果。

目标输出：

| 输出块 | 内容 | 证据要求 |
|---|---|---|
| `leadSummary` | 今日最重要的信息概述 | 引用候选内容 |
| `topicClusters` | 主题归并 | 每组至少 1 条来源 |
| `sourceHighlights` | 关键来源摘要 | 指向 content ref 或 summary result |
| `recommendationReasons` | 为什么推荐给当前用户 | 引用兴趣、历史行为或内容标签 |
| `uncertainties` | 材料不足或不确定项 | 明确说明限制 |

执行步骤：

1. 确认 Today 当前正式读侧仍以 `dashboard/today` 和 `briefings.payload` 为主。
2. 梳理候选事实输入：
   - `rss_articles`
   - `hot_topics`
   - `opportunities`
   - `article_processing_results`
   - `hot_topic_processing_results`
   - `summary_generation_results`
   - `user_interests`
3. 新增或扩展简报生成服务，保持规则结构为主，LLM 只生成文本块和归并解释。
4. 写入 `briefings.payload`，保留 `status/generated_at` 等现有字段口径。
5. 前端 Today 和历史简报读取同一 payload 结构。
6. 失败时展示规则摘要，并标记 `fallback`。

验收标准：

1. 今日简报可生成 LLM 摘要、主题归并、来源引用、推荐理由。
2. 历史简报能展示当时生成的结果，不因今日重新生成而漂移。
3. Provider 不可用时仍展示规则简报。
4. LLM 输出不直接写入内容事实表。
5. 至少补一组 route 或 service 测试覆盖成功、fallback、非法 JSON。

边界：

1. 不在本阶段做完整 RAG 或长期记忆层。
2. 不让 LLM 全量重排所有内容，只处理候选集解释、归并与摘要。
3. 不引入未落地字段名，例如不直接假设 `briefings.result_payload` 已存在。

### P7-C 信息源整理进入 LLM 可控子流程

目标：

在现有结构化数据与规则聚合基础上，引入 LLM 做来源去重、主题归并、可信度解释和推荐理由生成。

执行策略：

1. 规则层继续负责抓取、基础过滤、去重主键、时效性和基础排序。
2. LLM 只处理已进入候选池的内容。
3. 对明显高分和明显低分内容不调用 LLM。
4. 对相似标题、同源转载、主题相近但表达不同的候选内容做聚合解释。

输出建议：

```json
{
  "clusters": [
    {
      "title": "主题名称",
      "summary": "主题摘要",
      "sourceRefs": [],
      "confidenceNote": "可信度解释",
      "recommendationReason": "推荐理由"
    }
  ],
  "dedupedRefs": [],
  "uncertainties": []
}
```

验收标准：

1. 同一主题的多条来源能归并展示。
2. 推荐理由能引用用户兴趣或行为事实。
3. 可信度解释不编造来源权威性，只基于来源、重复出现、时间和内容一致性描述。
4. LLM 失败时保留原规则列表。

### P7-D 成本、限流、重试与熔断治理

目标：

让 LLM 调用具备可控的工程边界，避免单用户、单页面或失败重试造成不可控成本。

最小治理项：

| 治理项 | 第一版策略 | 落点建议 |
|---|---|---|
| 用户级日配额 | 按 feature 计数，先软限制 | `llm_invocations` 聚合 |
| Feature 级开关 | Chat/Report/Profile/Briefing 分开 | 环境变量或用户设置 |
| 超时 | 短文本 8-12s，报告/简报 20-30s | `chatCompletion` options |
| 重试 | 仅网络/429/5xx 最多 1 次 | provider transport |
| 熔断 | 同 provider 连续失败后短时间走 fallback | 内存或 D1 轻量状态 |
| 成本估算 | 先按输入/输出字符估算 | 诊断页 |

验收标准：

1. 单个用户无法连续触发无限重新生成。
2. 常见 provider 失败能记录错误类型，并进入 fallback。
3. 诊断页能按 feature/provider/model 查看数量、失败率、平均耗时。
4. 成本估算可标记为估算值，不伪装为真实账单。

### P7-E 系统诊断页增强

目标：

把当前开发诊断入口从“能看调用统计”增强为“能定位失败样本和成本风险”。

执行步骤：

1. 时间窗口切换：
   - 1 小时
   - 24 小时
   - 7 天
   - 30 天
2. 失败样本列表：
   - 时间
   - feature
   - provider/model
   - error_code
   - duration_ms
   - request_id 或 invocation id
3. 成本估算：
   - input_chars
   - output_chars
   - estimated_tokens
   - estimated_cost
4. 失败样本跳转：
   - 第一版可跳到诊断详情或复制 invocation id
   - 暂不直接跳业务页面，避免权限与上下文混乱

验收标准：

1. 诊断页能按时间窗口刷新。
2. 失败样本可定位到 `llm_invocations` 记录。
3. 成本显示有“估算”标识。
4. 普通用户入口不暴露开发诊断信息。

## 4. 推荐执行顺序

### 第一批：状态统一优先

先做 P7-A。

原因：

1. 已有报告、画像、简报、Chat 多条 LLM 链路，用户侧状态不统一会放大产品割裂感。
2. 今日简报和治理都需要承载 `generating/fallback/failed/stale` 状态。
3. 该工作可与当前 P4 页面迁移并行，不要求先重构后端。

交付物：

1. AI 状态枚举与文案表。
2. 报告页/画像页/简报页状态接入点清单。
3. 至少报告页和画像页完成同口径状态展示。

### 第二批：今日简报正式链路

再做 P7-B 和 P7-C。

交付物：

1. 简报 LLM payload schema。
2. Briefing 生成 service。
3. Today/历史简报展示收口。
4. 成功、fallback、历史读取测试。

### 第三批：工程治理和诊断页增强

最后做 P7-D 和 P7-E。

交付物：

1. 配额、重试、超时、熔断策略第一版。
2. 诊断页时间窗口和失败样本列表。
3. 成本估算说明和 UI。

## 5. 与当前 P4 页面迁移主线的协同边界

当前 `当前阶段总表.md` 仍以 P4 正式页面迁移为主线。P7 本文档只作为 LLM 产品化并行线，不抢占 P4 主控文档。

协同规则：

1. 不修改 P4 主线文档的阶段定义。
2. 不替换 P4 页面迁移计划。
3. 如果 P7 需要改动正式页面，只做状态和生成结果承载，不顺手做大版式重构。
4. 如果 P4 正在改同一页面，P7 优先产出接口、状态契约和文案表，等页面批次合并后再接入。
5. 如果必须同时改同一文件，应先查 `git status` 和最新 diff，再只做最小局部改动。

## 6. 风险与回退

| 风险 | 表现 | 回退方式 |
|---|---|---|
| 状态字段过早统一后端 | 牵动多表 migration | 第一版只做前端映射和 payload 兼容 |
| 今日简报 schema 过大 | LLM JSON 不稳定 | 文本块分段生成，失败回退规则摘要 |
| 信息源整理成本过高 | 候选内容过多导致调用放大 | 只处理候选池和模糊区间 |
| 诊断页暴露敏感信息 | 错误详情包含 prompt 或用户内容 | 诊断页只展示截断摘要、错误码和 id |
| 重试策略放大成本 | 失败时重复扣费 | 只对网络/429/5xx 重试 1 次 |
