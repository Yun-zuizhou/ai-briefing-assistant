## 当前判断

第一阶段已从“边界污染治理”推进到“复杂中心拆分”，随后修正为“接口清晰优先”。当前已经降低了正式门槛、API 基础设施、Chat SSE 和诊断页 hook 的返乱概率；`api.ts` 已基本回到 API 方法编排职责。后端 Today 链路现在有明确 public API：route 调 `loadTodayPageData()`，scheduler 调 `runTodayBriefingCron()`，内部 content/payload/store/generation 不通过 barrel 暴露。本轮已开始把同一原则迁移到 Chat：route 调 `createChatMessageStream()`、`confirmChatMessage()`、`reclassifyChatMessage()`，不再直接掌握后端 Chat 协议编排。

仍未根治的是跨端协议事实源：Chat SSE event、Chat request/response、前端 `useChatLogic` 状态迁移仍未进入共享 schema。当前治理已避免继续沉迷 dashboard 局部最优，但还只是把“后端 Chat 编排入口”立起来，下一步必须处理前端 hook 与共享契约。

后续治理顺序：

1. 定义 Chat 跨端协议契约：message stream event、confirm/reclassify request、execution result response。
2. 将 `apps/web/src/hooks/useChatLogic.ts` 的 SSE event handling 收敛为 reducer / 状态机入口，避免前端 hook 继续内嵌协议细节。
3. 继续按 public API 优先原则治理 `apps/web/src/services/api.ts`：先定义页面级 API 入口，再迁移内部 guard。
4. 将前端手写运行时 guard 逐步迁入共享契约或共享 schema。
