# 2026-05-01 Settings 配置落点 UX 规格

## 1. 页面定位

`/settings` 是系统配置的导航和状态摘要页，不是所有配置项的内联编辑页。

它要回答用户一个问题：

> 我刚才在对话、引导或设置详情页里改过的东西，现在系统认不认？

因此，设置相关页面分为三层：

1. `/settings`：配置目录、轻量状态摘要、跳转入口。
2. `/notification-settings`：简报通知配置的唯一编辑页。
3. `/ai-provider-settings`：AI 服务能力配置页，属于高级设置，不进入普通对话配置链路。

## 2. 与 Chat 配置链路的关系

Chat 可以承接自然语言配置，但不能替代设置详情页。

正式链路：

```text
Chat 输入配置意图
-> Chat 展示确认
-> 后端写入正式配置
-> Chat 展示配置成功
-> 跳转对应设置详情页验证
```

当前已纳入 Chat 配置链路的设置：

- 新增关注领域；
- 移除关注领域；
- 设置晨间简报推送时间。

当前不纳入 Chat 配置链路的设置：

- AI Provider / API Key；
- 登录、注册、退出；
- 删除账号或清空数据；
- 通知免打扰和提醒方式。

## 3. `/settings` 信息架构

主层级：

1. AI API：高级能力配置入口。
2. 通知设置：显示当前晨间/晚间时间和免打扰状态，进入详情页编辑。
3. 外观和基础偏好：主题、装饰强度、语言。
4. 提醒方式轻量偏好：声音、震动。

规则：

- 只有能立即同步且契约明确的轻量项可以在 `/settings` 直接编辑。
- 需要多个字段共同保存的配置必须进入详情页。
- 同一个正式配置不能同时在首页和详情页以两个编辑器存在。
- 首页可展示摘要，但不复制详情页表单。

## 4. `/notification-settings` 页面职责

页面名称：通知设置。

职责：

- 编辑晨间简报和晚间简报时间；
- 编辑免打扰时段；
- 编辑声音和震动提醒；
- 明确保存状态；
- 承接 Chat 配置成功后的验证跳转。

非职责：

- 不展示关注领域；
- 不配置 AI Provider；
- 不管理待办提醒生命周期；
- 不提供无法保存到后端的开关。

## 5. 控件真实性规则

通知页只展示后端能够保存的控件。

当前后端契约保存：

- `morning_brief_time`
- `evening_brief_time`
- `do_not_disturb_enabled`
- `do_not_disturb_start`
- `do_not_disturb_end`
- `sound_enabled`
- `vibration_enabled`

因此，页面不展示“晨间简报启用/停用”“晚间简报启用/停用”这种独立开关，除非后端补上对应字段和调度语义。

## 6. 成功反馈

配置成功必须满足：

- 用户知道已经保存；
- 用户知道保存到哪里；
- 用户能回到对应详情页复核；
- 页面文案不把“正在编辑”伪装成“已经生效”。

推荐文案：

- Chat 成功：`配置成功：简报推送时间已设为 08:00。`
- 通知页保存：`配置已保存`
- 设置首页脚注：`对话中确认过的系统配置会同步到这里；通知时间由通知设置页统一管理。`

## 7. 后续扩展规则

新增配置项时先判断归属：

- 单字段、可立即保存、低风险：可放 `/settings`。
- 多字段组合、需要解释、需要保存按钮：放详情页。
- 涉及密钥、安全、账号：独立设置页。
- 涉及用户关注：优先走兴趣配置页或 Chat 确认链路，不塞进通知页。

新增配置项必须补：

- 页面契约；
- 后端字段或明确的只读来源；
- 成功反馈；
- 失败反馈；
- 至少一条验证测试或人工验收项。
