## 1. 本批目标

P7-A 先解决用户侧“AI 正在做什么、结果从哪里来、失败后是否回退、能否重新生成”的一致性问题。

第一批不做大重构，只做三件事：

1. 定义统一状态枚举。
2. 把现有字段映射到统一状态。
3. 形成页面接入点和验收清单。

---

## 2. 统一状态枚举

| 状态 | 定义 | 用户侧主文案 | 辅助文案方向 | 主操作 |
|---|---|---|---|---|
| `idle` | 尚未生成 AI 内容 | 暂无 AI 内容 | 可基于当前数据生成 | 生成 |
| `generating` | 当前请求已触发且未返回 | 正在生成 | 请稍候，生成完成后会刷新 | 禁用重复提交 |
| `success` | AI 内容生成成功 | 已生成可追溯 AI 内容 | 展示 provider/model/生成时间/证据 | 查看依据、重新生成 |
| `fallback` | AI 未成功但规则结果可用 | 当前为规则结果 | AI 暂不可用，已展示规则结果 | 重新生成 |
| `failed` | 没有可展示结果 | 生成失败 | 可稍后重试 | 重试 |
| `stale` | 已有 AI 结果但事实已变化 | AI 内容可能不是最新 | 当前数据已更新，可重新生成 | 重新生成 |
| `readonly` | 历史对象只读 | 历史生成结果 | 保留当时内容，不支持重新生成 | 查看 |

统一原则：

1. 用户侧只展示“规则结果/AI 结果/生成中/失败/可重新生成”，不展示底层错误堆栈。
2. `fallback` 不能写成失败空白页，必须保留已有规则内容。
3. `readonly` 用于历史报告、历史简报等对象，不出现“重新生成”按钮。
4. provider/model 是补充信息，不作为状态本身。

## 3. 现有字段映射

### 3.1 周报/月报

已存在字段：

- `PeriodicReportData.generationSource?: 'rules' | 'llm'`
- `PeriodicReportData.llmBlocks?: PeriodicReportLlmBlocks`
- `PeriodicReportLlmBlocks.provider`
- `PeriodicReportLlmBlocks.model`
- 页面刷新入口：`getWeeklyReport({ refresh: true })`、`getMonthlyReport({ refresh: true })`

映射规则：

| 条件 | 状态 |
|---|---|
| 当前请求 loading | `generating` |
| `llmBlocks` 存在且 `generationSource=llm` | `success` |
| 无 `llmBlocks` 且页面有规则报告 | `fallback` |
| 带 `reportId` 的历史报告 | `readonly` |
| 请求失败且无旧数据 | `failed` |

当前页面现状：

1. `WeeklyReportPage.tsx` 已展示“已生成可追溯 AI 解读 / 当前为规则周报”。
2. `MonthlyReportPage.tsx` 已展示“已生成可追溯 AI 解读 / 当前为规则月报”。
3. 两者已有重新生成按钮和 loading label。

第一批执行建议：

1. 抽出统一文案函数，减少周报/月报重复判断。
2. 把 `当前为规则周报/月报` 统一为 `当前为规则结果` 或保留对象名但共用状态源。
3. 重新生成失败时使用同一失败提示文案。

### 3.2 年报

已存在字段：

- `AnnualReportData.generationSource?: 'rules' | 'llm'`
- `AnnualReportData.annualLlmBlocks?: AnnualReportLlmBlocks`
- `AnnualReportLlmBlocks.provider`
- `AnnualReportLlmBlocks.model`

映射规则：

| 条件 | 状态 |
|---|---|
| 当前请求 loading | `generating` |
| `annualLlmBlocks` 存在且 `generationSource=llm` | `success` |
| 无 `annualLlmBlocks` 且页面有规则年报 | `fallback` |
| 请求失败且无旧数据 | `failed` |

当前页面现状：

1. `AnnualReportPage.tsx` 已展示“已生成可追溯 AI 年度解读 / 当前为规则年报”。
2. 年报使用 `deepseek-v4-pro` 的模型策略已在 P6 文档中明确。

第一批执行建议：

1. 与周报/月报共用同一状态映射。
2. 年报仅保留对象名差异，不另起一套状态文案。

### 3.3 用户画像

已存在字段：

- `profileData.ai_generated`
- `profileData.persona_generated_at`
- `profileData.persona_provider`
- `profileData.persona_model`
- `profileData.evidence_refs`
- 页面动作：重新生成画像

映射规则：

| 条件 | 状态 |
|---|---|
| `generateLoading=true` | `generating` |
| `ai_generated=true` | `success` |
| `ai_generated=false` 且有 `persona_summary` | `fallback` |
| 无画像数据且无生成请求 | `idle` |
| 请求失败且无画像数据 | `failed` |

当前页面现状：

1. `ProfilePage.tsx` 已展示“LLM 画像已生成 / 当前为规则画像”。
2. 已展示 provider/model、生成时间、证据来源。
3. 已有“重新生成”按钮。

第一批执行建议：

1. 将 `LLM 画像已生成` 改为统一语义的 `已生成可追溯 AI 画像`。
2. 将 `当前为规则画像` 纳入统一 `fallback` 文案体系。
3. 生成失败时区分“保留旧结果”和“无结果失败”。

### 3.4 今日简报与历史简报

已存在基础：

- `briefings` 表存在 `status/generated_at/payload` 口径。
- `dashboard/today` 当前读取 `briefings` 作为 Today 相关数据来源之一。
- `HistoryBriefPage.tsx` 当前以报告历史为主，已有 `generatedAt/available` 文案。

当前缺口：

1. 今日简报还未形成正式 LLM payload 状态。
2. 历史简报展示尚未完全收口到“当时生成结果”。
3. 简报缺少与报告同一套 `success/fallback/readonly` 状态。

第一批执行建议：

1. P7-A 先定义状态映射，不立即改表。
2. P7-B 再补简报 LLM payload schema。
3. 历史简报只读态使用 `readonly`，不提供重新生成。

### 3.5 Chat 与内容咨询

已存在基础：

- Chat LLM 分类、回复和上下文已经接入，失败时回退规则。
- Content consult 已有 summary/consult 相关能力。
- `llm_invocations` 可记录调用状态。

当前缺口：

1. Chat 回复不适合暴露完整 AI 状态卡片，但需要失败时不把失败伪装成成功。
2. Content consult 是主动问答场景，需要 `generating/failed/fallback` 的轻量提示。

第一批执行建议：

1. Chat 只做轻量状态，不加重页面负担。
2. Content consult 使用同一套 loading 和失败文案。
3. 不把 `llm_invocations` 原始错误展示给普通用户。

## 4. 建议代码落点

第一批最小落点：

| 类型 | 建议位置 | 职责 |
|---|---|---|
| 类型定义 | `apps/web/src/types/page-data.ts` 或 `packages/contracts/src/page-data.ts` | 如需前后端共享，再放 contracts |
| 前端映射 | `apps/web/src/utils/aiGenerationStatus.ts` | 从 report/profile/briefing payload 映射统一状态 |
| 通用文案 | `apps/web/src/utils/aiGenerationStatus.ts` | 返回 title/detail/action label |
| 页面接入 | Report/Profile/Today/Consult 页面 | 使用统一映射，不重复写判断 |
| 样式 | 复用现有 report/profile 状态卡样式 | 不在本批引入大 UI 重构 |

第一版建议先放前端 `utils`，原因：

1. 现有后端 payload 尚不完全一致。
2. P7-A 主要是用户侧体验统一，不应先牵动 migration。
3. 后续 P7-B 简报 schema 稳定后，再判断是否上升到 contracts。
