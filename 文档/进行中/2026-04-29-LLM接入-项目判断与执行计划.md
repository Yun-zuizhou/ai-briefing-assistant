## 0. 当前结论

AI简报助手的主闭环是：

`今日信息 -> 内容理解 -> 对话/行动转化 -> 个人沉淀 -> 周期回顾`

LLM 不应被接成“到处调用模型”的横向能力，而应作为可观测、可回退的智能加工层。规则引擎、数据库事实、权限校验和写入动作仍然是主链路；LLM 只承担模糊理解、内容压缩、个性化解释和自然表达。

### 0.1 两条运行链路

| 链路 | 运行时 | 当前已有基础 | 未来职责 |
|------|--------|--------------|----------|
| 实时链路 | Cloudflare Workers + Hono | 用户级 AI Provider 设置、Digest consult、Chat SSE | Chat 意图分类、自然回复、摘要咨询、轻量画像读取增强 |
| 批处理链路 | Python executor | `summary_generation_tasks/results`、`run_summary_executor.py`、`ai_processing_runs` | 信息源整理、摘要生成、简报文本块、批量画像刷新 |

|------|----------|------|
| Provider 配置 | `apps/edge-worker/src/services/ai-provider.ts` | 已有平台定义和用户配置解析，但缺少通用调用函数 |

## 1. 总体接入原则

1. **LLM 不直接写库**：LLM 只返回结构化建议，真实写入仍由现有 service/action 层完成。
2. **规则永远是降级路径**：无 provider、调用超时、JSON 解析失败、Schema 不合法时，不阻断主流程。
3. **每个能力封装为 Skill**：每个 Skill 必须定义 Trigger、Input、Prompt、Output Schema、Validation、Fallback、Metrics。
4. **先接高收益低风险链路**：先 Chat 低置信分类，再自然回复，再信息筛选与画像，不先让 LLM 接管完整报告。
5. **只传必要事实，不传秘密**：Prompt 中不出现 API Key、session secret、internal token，不传无关用户隐私。
6. **输出必须校验**：JSON Skill 强制解析和字段值域校验；纯文本 Skill 做长度、空值、敏感词过滤。
7. **所有调用可观测**：至少记录 skill、provider、model、duration、success、error_type、tokens_used、fallback_used。

## 2. Skill 清单

| Skill | 用途 | 运行位置 | 触发 | 输出 | 降级 |
|------|------|----------|------|------|------|
| `classify_intent` | Chat 意图识别 + 实体抽取 | Workers | 规则低置信 | JSON | `parseIntent()` |
| `generate_reply` | 助手自然回复 | Workers | Chat 执行后 | 短文本 | `buildAssistantReplyText()` |
| `consult_content` | 针对摘要结果问答 | Workers | 用户主动咨询 | JSON | provider 错误提示 / debug fallback |
| `evaluate_relevance` | 信息源相关性复判 | Python | 关键词分 40-80 | JSON | 当前关键词评分 |
| `summarize_content` | 单条内容摘要 | Python | 摘要任务队列 | JSON | debug fallback |
| `analyze_user` | 画像 + 成长洞察 | Workers 或 Python | 每日/每周/数据变化 | JSON | `buildPersonaSummary()` + `buildGrowthKeywords()` |
| `generate_report_blocks` | 周/月/年报解释文本块 | Python | 报告生成 | JSON 文本块 | 当前规则报告 |

## 3. 接入阶段

### 阶段 P0：LLM 基础设施收口

**目标**：所有 LLM 调用走统一入口，先把“怎么调用模型”从业务里抽出来。

改动步骤：

1. 在 `apps/edge-worker/src/services/ai-provider.ts` 增加 `chatCompletion()`、`extractText()`、`splitSystemMessage()`。
2. 将 `apps/edge-worker/src/services/content/consult.ts` 内部的 `requestConsultProvider()` 和 `extractProviderText()` 改为调用公共函数。
3. 补齐 `local` provider 口径：README、Python、同步脚本已支持 `local`，Workers 类型层当前未支持，需要统一。
4. 增加基础调用选项：`temperature`、`maxTokens`、`signal`、`timeoutMs`。
5. 增加统一错误类型：`provider_not_configured`、`provider_request_failed`、`provider_timeout`、`invalid_model_output`。
6. 明确 API Key 风险处理：短期不扩大明文使用面；中期新增加密存储或改为用户自带 provider token 代理机制。

验收：

- `consultDigestResult()` 外部行为不变。
- 支持 openai-compatible、anthropic、gemini、qwen、local 五类 transport。
- provider 不可用时只进入 fallback，不影响非 LLM 功能。
- `npm.cmd run check` 通过。

回退：

- 保留 `consult.ts` 原业务接口不变，只回退内部 transport 提取。

---

### 阶段 P1：Chat 低置信意图分类

**目标**：只在规则引擎不够确定时调用 LLM，提高 Chat 对自然语言、模糊表达、组合意图的理解能力。

改动步骤：

1. 新建 `apps/edge-worker/src/services/chat/llm-classify.ts`。
2. 定义 `ChatClassifyResult`，与 `ParsedIntentResult` 可互换。
3. 增加 `buildClassifyPrompt()`，只传用户输入、当前关注、来源上下文、必要候选意图。
4. 增加 `parseClassifyJSON()`，校验 intent 白名单、confidence、entities、candidateIntents、replyHint。
5. 在 `routes/chat.ts` 中判断触发条件：
   - `matchedBy=fallback`
   - `matchedBy=fuzzy`
   - `matchedBy=keyword && confidence < 0.88`
   - `matchedBy=pattern && confidence < 0.88`
6. LLM 成功时只替换 `intentType/entities/candidateIntents/replyHint`，执行仍走 `executeConfirmedChatAction()`。
7. SSE `intent_analysis` 增加 `llmClassified`、`replyHint`、`suggestedActions`，保持向后兼容。

验收：

- 未配置 provider 时 Chat 完全按原规则运行。
- LLM JSON 非法时自动回退规则结果。
- 写入动作仍由现有 action 层执行。
- 低置信样例人工验证：取消关注、模糊统计、自然问候、组合表达。

回退：

- 删除 `llm-classify.ts` import 和 `needsLLM` 分支即可恢复。

---

### 阶段 P2：Chat 自然回复

**目标**：替换硬编码的助手回复，让 Chat 更像一个真实助手，但不影响执行结果。

改动步骤：

1. 在 `llm-classify.ts` 或 `services/chat/llm-reply.ts` 增加 `generateReply()`。
2. 输入只包含用户原话、actionType、success、resultSummary，不传完整隐私上下文。
3. 输出限制为 1 句，普通动作不超过 35 字，`chat_only` 最多 2-3 句。
4. `routes/chat.ts` 中优先使用 `replyHint`，缺失时调用 `generateReply()`，失败时回退 `buildAssistantReplyText()`。
5. 对失败回复做安全限制：不能承诺已经写入、不能编造执行结果。

验收：

- `chat_only` 不再出现“好的，这次不保存内容”这类机械回复。
- 失败时不会把失败包装成成功。
- LLM 超时不影响消息写入。

回退：

- 关闭 `generateReply()` 分支，继续使用原模板。

---

### 阶段 P3：多轮上下文与指代消解

**目标**：让 Chat 能理解“刚才那个”“第一个”“它”等上下文指代。

改动步骤：

1. 在 `services/chat/store.ts` 增加 `getRecentChatMessages(db, sessionId, limit)`。
2. `routes/chat.ts` 在分类前取最近 3-5 条 user/assistant 消息。
3. Prompt 中历史消息每条截断到 120 字，只传角色、内容、intentType。
4. 对指代类低置信输入启用上下文；普通明确指令不强制带历史。
5. 增加上下文开关，便于回退。

验收：

- 人工样例：
  - “最近有什么机会” -> “第一个帮我盯着”
  - “记下明天交周报” -> “改成后天”
  - “帮我关注 AI” -> “刚才那个也加到远程工作”
- 带历史后平均分类耗时增量可接受。

回退：

- 不传 `recentMessages`，保留单轮分类。

---

### 阶段 P4：信息源整理与相关性复判

**目标**：提升信息源筛选质量，不让 LLM 承担全量过滤成本。

改动步骤：

1. 在 `app/services/directed_digest.py` 保留现有关键词、黑名单、白名单、信任度、新鲜度评分。
2. 增加 `evaluate_relevance`，只处理规则评分 40-80 的模糊候选。
3. Prompt 输入：用户兴趣、近 7 天互动类型、标题、摘要、来源、当前评分拆解。
4. 输出 Schema：
   - `score: 0-100`
   - `reasons: string[]`
   - `tags: string[]`
   - `actionability: high | medium | low`
5. 解析失败则沿用原规则分。
6. 将 LLM 复判结果写入 `score_breakdown`，便于后续审计。

验收：

- 明确高分和低分内容不调用 LLM。
- 模糊区间样本人工抽检 50 条。
- 用户“不相关”反馈率可对比下降。

回退：

- 关闭模糊区间复判，恢复纯规则排序。

---

### 阶段 P5：用户画像与成长洞察

**目标**：把当前模板画像替换为基于事实的个性化画像和周期洞察。

改动步骤：

1. 新增 `analyze_user` Skill。
2. 输入只使用聚合事实：
   - 关注兴趣
   - 笔记数、收藏数、完成待办、历史行为数
   - 最近笔记摘要、最近收藏标题、最近行动记录
   - 上次画像结果
3. 输出 Schema：
   - `persona.summary`
   - `persona.keywords[{word, weight, trend}]`
   - `persona.traits`
   - `insights[{title, detail, evidence}]`
   - `suggestions`
4. 结果写入 `user_profiles.summary/profile_data`。
5. `preferences/profile` 和 `growth-overview` 优先读缓存画像，无缓存或失败时回退当前 `buildPersonaSummary()`。
6. 24 小时缓存，或新增 5 条以上事实后刷新。

验收：

- 用户可见画像不再是固定模板句。
- 每条 insight 必须有 evidence。
- 数据稀疏时明确说明数据不足，不编造趋势。

回退：

- 页面继续使用 `buildPersonaSummary()`、`buildGrowthKeywords()`。

---

### 阶段 P6：简报与周期报告文本块标准化

**目标**：不让 LLM 直接生成整份页面 payload，而是生成可校验的解释文本块。

改动步骤：

1. 保留 `reports/builder.ts` 的结构化规则 payload。
2. 新增 `generate_report_blocks`，只生成：
   - 趋势解释
   - 周期总结
   - 下一步建议
   - 数据不足说明
3. 每个文本块要求携带 `evidence_refs`，引用 notes/favorites/todos/history 的聚合事实。
4. Python executor 或 Workers 定时任务负责生成并写入报告 payload。
5. 页面只展示已通过 Schema 校验的文本块。

验收：

- 报告结构稳定，LLM 失败时仍可展示规则报告。
- 文本块不出现无证据判断。
- 周报/月报/年报都能降级。

回退：

- 忽略 LLM 文本块，继续使用当前 builder 文案。

## 6. 风险与处理

| 风险 | 位置 | 处理 |
|------|------|------|
| API Key 明文存储 | `user_settings.ai_api_key` | P0.5 已新增 `ai_api_key_encrypted`；新保存写密文并清空明文；已补历史迁移接口与触发器防止新写明文 |
| Prompt 注入 | Chat / consult / digest | 系统提示隔离、输入截断、输出 Schema 校验 |
| Token 失控 | 所有 Skill | 每个 Skill 固定 maxTokens，历史消息截断 |
| 延迟过高 | Chat | 意图分类只在低置信时调用；DeepSeek v4 pro 为 reasoning 模型，分类/回复需更长 timeout，并保留模板回退 |
| JSON 不稳定 | 所有结构化 Skill | fenced JSON 提取、Schema 校验、失败 fallback |
| LLM 编造 | 摘要/报告/画像 | 强制 evidence；数据不足必须显式说明 |
| 供应商差异 | 多 provider | 公共 transport + extractText 统一兼容 |

## 7. 当前执行建议

下一步不要直接接画像或报告。最合理的第一个实现批次是：

1. P0：公共 transport 收口。
2. P1：Chat 低置信意图分类。
3. P1 验证稳定后，再做 P2 回复生成。

原因：

- Chat 链路现在规则和写入层已经稳定，LLM 只做增强，回退简单。
- `consult.ts` 已经有可复用的 provider 调用代码，抽 transport 成本低。
- 画像和报告更容易产生“看起来对但事实不稳”的输出，应该等日志、Schema、fallback 基础设施稳定后再接。
