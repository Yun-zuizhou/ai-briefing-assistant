# Chat 架构重构方案

- 建立日期：2026-04-29
- 文档定位：从"局部最优补丁"到"完整对话架构"的分阶段重构方案

---

## 0. 现状诊断摘要

| 问题 | 严重程度 | 影响 |
|------|----------|------|
| localStorage 持久化层已成死代码（写入后下次加载被模块级代码删除） | 中 | ~100 行无效代码，混淆数据流认知 |
| 挂载时 4 次 HTTP 请求（StrictMode × effect 双重触发） | 中 | 每次页面加载多余 2 次请求 |
| SSE 流结束后全量重取只为 ID 对齐 | 中 | 多余 1 次 HTTP 往返 + UI 抖动 |
| Intent analysis bubble 在刷新后消失（未入库的瞬时幻影） | 中 | 用户看到消息闪现后消失 |
| 确认流程 DB 重复写入 user 消息 | **高** | 数据库脏数据 |
| `PersistedChatMessage` 与 `ChatSessionMessage` 类型重复定义 | 低 | 维护两套相同结构 |
| 模块级 localStorage 清理（import 时执行副作用） | 低 | 反模式，时机不可控 |

## 1. 目标架构总览

### 1.1 数据流原则

```
┌─────────────────────────────────────────────────────────────┐
│                      前端状态                                │
│  messages: ChatSessionMessage[]    ← 唯一消息状态            │
│  messageLifecycle: Map<clientId, LifecycleState>             │
│  sessions: ChatSessionSummary[]                              │
│  currentSessionId: number | null                             │
└─────────────────────────────────────────────────────────────┘
        ▲                    ▲                    ▲
        │ 初始加载           │ 实时消息            │ 操作（删除等）
        │ REST GET           │ SSE stream          │ REST POST/DELETE
        │                    │                     │
┌───────┴────────────────────┴─────────────────────┴──────────┐
│                      后端                                    │
│  GET /chat/sessions          → 会话列表                      │
│  GET /chat/sessions/:id      → 会话 + 消息（支持分页）       │
│  POST /chat/message (SSE)    → 发送消息 + 流式返回            │
│  POST /chat/confirm          → 确认待定意图（新增）           │
│  POST /chat/reclassify       → 纠偏                          │
│  DELETE /chat/messages/:id   → 删除消息                      │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 核心变化

- **localStorage 完全移除**：不缓存、不持久化、不降级
- **单一句柄类型**：前端状态直接使用 `packages/contracts` 中的 `ChatSessionMessage`，不再定义 `PersistedChatMessage`
- **SSE 携带真实 messageId**：后端 `appendChatMessage` 的返回值通过 SSE 传回，前端用服务端 ID 替换临时 ID
- **新端点 `POST /chat/confirm`**：确认待定意图走独立端点，避免 `/chat/message` 的重复 user 消息 bug

### 阶段三：完整架构（预计改动 ~300 行）

**目标**：消息生命周期状态机、会话作为工作空间、操作溯源、多轮上下文。

#### 3.1 消息生命周期状态机

当前 `messageState` 字段已有雏形，但没有被系统性地使用。完整状态机：

```
                  ┌──────────┐
                  │  sending │  (仅前端，等待 SSE 连接)
                  └────┬─────┘
                       ▼
                  ┌──────────┐
                  │recognized│  (服务端已收到，意图解析中)
                  └────┬─────┘
                       ▼
              ┌────────┴────────┐
              ▼                 ▼
      ┌──────────────┐  ┌──────────────────┐
      │  processing  │  │pending_confirmation│
      │  (自动执行中) │  │  (等待用户确认)    │
      └──────┬───────┘  └────────┬─────────┘
             ▼                    ▼
      ┌──────────┐        ┌──────────────┐
      │ executed │        │  confirmed   │ (用户已确认)
      └──────────┘        └──────┬───────┘
                                 ▼
                          ┌──────────┐
                          │ executed │
                          └──────────┘

      任意非终态 ──→ ┌──────────┐
                     │  error   │ (可重试)
                     └──────────┘
```

**实现**：`LifecycleState` 类型定义在 `packages/contracts/src/page-data.ts`，SSE 事件和前端状态同步使用。

#### 3.2 SSE 事件流扩展

当前事件类型：`intent_analysis` → `pending_confirmation`/`execution_result`

扩展后：
```
message_ack     ← 消息已入库，携带 messageId
lifecycle       ← 状态变更通知（recognized → processing → executed）
intent_hint     ← 意图识别结果（瞬时，不持久化）
confirmation    ← 需要确认
execution_result← 执行结果
error           ← 可恢复错误（携带 retry 信息）
done            ← 流结束
```

**文件**：`apps/edge-worker/src/routes/chat.ts`

```typescript
// Event 0: 确认收到
const userMsgId = await appendChatMessage(...)
sendSSE(controller, 'message_ack', {
  clientMessageId: body.client_message_id,  // 前端可选传入
  messageId: userMsgId,
})

// Event 1: 意图提示（瞬时）
sendSSE(controller, 'intent_hint', {
  intentType,
  confidence,
  candidateIntents,
  label: intentLabel(intentType),
})

// Event 2: 生命周期
sendSSE(controller, 'lifecycle', {
  messageId: userMsgId,
  state: shouldConfirm ? 'pending_confirmation' : 'processing',
})

// Event 3: 确认或执行结果
if (shouldConfirm) {
  sendSSE(controller, 'confirmation', { ... })
} else {
  const assistantMsgId = await appendChatMessage(...)
  sendSSE(controller, 'lifecycle', {
    messageId: userMsgId,
    state: 'executed',
  })
  sendSSE(controller, 'execution_result', {
    messageId: assistantMsgId,
    userMessageId: userMsgId,
    // ...
  })
}
```

#### 3.3 会话作为工作空间

当前 `getOrCreateActiveSession` 确保每个用户有一个 active session。完整架构需要：

- **显式创建新会话**：`POST /chat/sessions` → 将当前 active 标记为 completed，创建新的 active
- **会话元数据**：`session_title`（自动从首条消息生成或用户手动命名）、`action_count`（该会话中执行的操作数）
- **会话归档**：`POST /chat/sessions/:id/archive` → 标记为 archived（不在默认列表中显示）
- **会话摘要**：首页可展示"最近对话摘要"

新增端点：
```
POST   /chat/sessions              → 创建新会话
PATCH  /chat/sessions/:id          → 更新会话（重命名等）
POST   /chat/sessions/:id/archive  → 归档
GET    /chat/sessions/:id/summary  → AI 生成的会话摘要
```

#### 3.4 操作溯源

当前 `affectedEntity` 已经在 assistant 消息中记录了受影响的实体。完整架构需要：

- **每个 executed action 都有 `actionTrace`**：包含 `actionType`、`affectedEntity`、`resultRef`（可跳转链接）
- **操作撤销**：`POST /chat/undo` → 撤销最近一次对话触发的操作（删除创建的 todo、恢复修改的 note 等）
- **操作历史视图**：在会话详情面板中展示"本次对话完成的操作"列表

**文件**：`packages/contracts/src/page-data.ts`

```typescript
export interface ChatActionTrace {
  messageId: number
  actionType: string
  affectedEntity: ChatExecuteAffectedEntity
  changeLog: ChatObjectChange[]
  undoable: boolean
  undoneAt?: string
}
```

#### 3.5 多轮上下文

当前每次 `sendMessage` 独立处理，不携带前序对话上下文。完整架构需要：

- **上下文窗口**：发送最近 N 条消息摘要给意图解析器（当前意图解析不需要，但未来接入 AI 时需要）
- **指代消解**："把刚才那个也标记为高优先级" → 需要知道"刚才那个"指的是哪个
- **上下文引用**：`source_context` 字段当前仅标记来源（article_action），应扩展为引用链

这些能力需要后端意图解析从规则匹配升级为 LLM 驱动，属于长期方向。阶段三仅完成数据结构预留。

#### 3.6 前端架构：Hook 拆分

当前 `useChatLogic.ts`（697 行）承担了所有职责。拆分为：

```
hooks/

  chat/
    useChatMessages.ts   ← 消息状态管理（~150 行）

```

## 6. 关键设计决策记录

1. **为什么不用 WebSocket**：Cloudflare Workers 不原生支持 WebSocket（Durable Objects 支持但引入额外复杂度）。SSE 满足单向推送需求。

2. **为什么不保留 localStorage 降级**：对话功能依赖服务端意图解析和数据库写入，离线状态下无法执行任何操作。localStorage 降级会制造"本地有数据但无法操作"的假象，不如明确告知用户需要网络连接。

3. **为什么 Intent analysis 改为瞬时提示而非持久化**：Intent analysis 是"思考过程"而非"对话内容"。用户不关心系统如何判断意图，只关心判断结果。保留为 2 秒 toast 既提供透明度，又不污染消息列表。

4. **为什么新增 `/chat/confirm` 而非修复 `/chat/message`**：两个操作语义不同——`/chat/message` 是"发送新消息并解析意图"，`/chat/confirm` 是"确认已解析的意图并执行"。分开端点使各自逻辑更清晰，也避免了 `append_user_message` 的条件分支。
