# 2026-05-01 UX 收口索引与开发检查清单

## 1. 用途

这份文件不是新的治理任务清单，而是开发期的判断入口。

目标是让新增页面、调整 UI、接后端能力时，先判断“这件事应该放在哪里、是否会改变用户路径、是否需要更新页面契约”，避免每次都重新设计结构，也避免把小改动升级成大治理。

默认原则：

- 能沿现有页面职责完成，就不要新增页面；
- 能沿现有组件接口完成，就不要新建一套组件体系；
- 能沿现有数据契约完成，就不要在页面里临时拼数据；
- 信息密集页先沿 `文档/进行中/2026-05-01-信息密集页设计模板.md` 和 `information-page` 模板判断阅读流；
- 只有用户任务、信息层级、主动作、后端可见数据契约发生变化时，才启动 UX 复核。

## 3. 开发前决策树

新增或大改 UI 前，先按这个顺序判断：

1. 这是内容消费吗？
   - 当天个性化内容：放简报；
   - 单条内容详情：放 Article；
   - 公共热点：放 Hot Topics。
2. 这是用户要执行或跟进的事情吗？
   - 有开始、完成、延期、跟进状态：放 Todo/Actions；
   - 只是从内容里产生候选行动：原页面只负责入口，生命周期交给 Todo/Actions。
3. 这是对话驱动的配置或执行吗？
   - 需要自然语言理解、用户确认、写入结果：走 Chat 的确认链路；
   - 不要让普通按钮静默改系统配置。
4. 这是个人沉淀吗？
   - 用户主动写下：Journal；
   - 用户主动保存：Collections；
   - 系统自动记录：History Logs。
5. 这是系统配置吗？
   - 设置总览：Settings；
   - 具体编辑：对应 detail page；
   - 高级/内部能力：低权重入口，不进入每日主路径。
6. 这是周期解释吗？
   - 周报、月报、年报负责解释；
   - Growth 只做概览和导航，不吞并报告正文。

## 4. 什么时候必须启动 UX 复核

满足任一条件，就需要先复核 UX，再进入实现：

- 新增 route 或把一个辅助页面提升为主路径；
- 新增页面主动作，或改变原页面主动作；
- 同一个对象开始出现在三个以上页面，并且每处动作不同；
- 后端返回的新字段会改变页面层级、按钮状态或用户判断；
- 一个页面里出现两个以上独立演化的业务块，且它们有不同数据源、状态和动作；
- 一个按钮会写入后端状态，但没有 loading、成功、失败反馈；
- 文案改变了产品含义，例如把“简报”改成“任务”、把“画像”改成“诊断”；
- 内部页、实验页、调试页准备进入普通用户导航。

## 5. 什么时候不启动 UX 治理

这些情况默认不升级成治理：

- 修复错别字、按钮对齐、间距、颜色、响应式断点；
- 在已有 section 内补充一个低风险字段；
- 修复 loading、empty、error 的显示问题；
- 给现有行为补测试；
- 组件内部实现重构，但页面职责、数据契约和用户动作不变；
- 沿已有模板新增一个同类页面，且没有新主流程。

## 6. 合并前最低检查

每次新增页面或大改 UI，至少检查：

- 页面职责能在 `apps/web/src/pages/README.md` 中找到或补齐；
- 页面入口、主动作、下游出口与页面契约一致；
- 后端写操作有 loading、成功、失败反馈；
- 用户看见的数据来自明确 API 或明确 fallback，不是页面临时编故事；
- 信息密集页已区分总述、主稿、分组阅读、辅助入口和隐藏处理数据；
- 样式进入页面或组件的 owning stylesheet，不进入 `index.css`；
- 组件通过公开接口被使用，不深挖内部实现；
- 用户可见文案不暴露内部术语，如 `LLM`、`payload`、`规则聚合`、`统一引用`；
- 改动没有让 Settings、Growth、Chat、Today 变成万能容器。

## 7. 收口结论

当前 UX 治理可以收口为一条开发规则：

```text
先确认用户意图，再确认页面职责，再确认数据契约，最后才写组件和样式。
```

后续不需要为了“继续治理”主动翻辅助页。只有当开发改动触发第 4 节条件时，才回到这份清单和对应页面规格。
