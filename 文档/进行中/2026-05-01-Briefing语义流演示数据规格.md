# 2026-05-01 Briefing 语义流演示数据规格

## 1. 目标

本轮不是先美化简报页，而是先给简报页建立一批可验证的演示数据。

这批数据有两个用途：

- 作为数据库里的演示对象，让 `/today` 能展示一份语义稳定的简报；
- 作为后续数据采集、数据处理和 AI 加工的模板，说明原始内容最终应该怎样进入简报页。

## 2. 简报语义流

```text
用户关注
-> 候选来源
-> 内容处理
-> 简报筛选
-> AI 主题归并
-> 页面展示
-> 阅读 / 追问 / 速记 / 转待办
```

### 2.1 用户关注

关注项决定简报筛选的第一层，不应只用泛化词。

演示关注项：

- `AI应用`
- `远程工作`
- `写作素材`
- `数据自动化`

这些词要能在候选内容的标题、摘要、分类或标签中命中，方便后续验证排序和推荐理由。

### 2.2 候选来源

当前兼容实现里，简报页的“关注领域报道”和“精选热点”主要来自 `hot_topics`，可转待办线索来自 `opportunities`。

语义上应把 `hot_topics` 视为“今日内容候选”，不等同于猎奇热点。后续如果新增正式内容候选表，可以从这里迁移。

候选内容必须具备：

- 可读标题；
- 一句话摘要；
- 来源名和来源 URL；
- 发布时间；
- 分类和标签；
- 质量分和热度分。

当前演示 seed 仍把演示候选的 `hot_value` 设置到现有本地样本之上。原因不是鼓励后续真实系统靠手工抬分，而是为了保证这批演示数据在直接查看 `hot_topics` 时也足够稳定。

后端候选读取已经接入关注项排序：`/today` 先读取 `user_interests`，再让 `listHotTopics()` 用关注项命中、质量分、热度分共同排序。这样旧热点、猎奇热点或无关公共热点不会只因为热度高就压过用户关注语义。

### 2.3 内容处理

演示 seed 同步写入 `hot_topic_processing_results`，表示候选内容已经经过基础归一化。

这层用于指导后续处理流程：

- `normalized_title`：去除噪声后的标题；
- `normalized_summary`：可直接进入卡片的摘要；
- `normalized_category_labels_json`：页面可读分类；
- `normalized_tags_json`：筛选和关联用标签；
- `quality_score`：内容质量；
- `processing_version`：处理版本。

### 2.4 简报筛选

简报筛选应回答三个问题：

- 这条内容是否和用户关注有关；
- 这条内容今天是否值得放进简报；
- 它应该进入头版、关注报道、精选热点还是待办线索。

当前实现对应关系：

| 页面字段 | 数据来源 | 语义 |
| --- | --- | --- |
| `recommendedForYou` | `user_interests` + `hot_topics` | 按关注项分组的报道 |
| `worthKnowing` | `hot_topics` | 少量精选内容 |
| `worthActing` | `opportunities` | 可转交待办的后续线索 |
| `leadItem` | `briefings.payload` | 头版重点 |
| `aiBriefing` | `briefings.payload` | AI 归并后的摘要和主题簇 |
| `extensionSlots` | `briefings.payload` | 追问、保存、待办等低权重入口 |

### 2.5 AI 主题归并

AI 不应重新发明内容，也不应编造用户任务。它的责任是把候选内容整理成阅读摘要。

演示 payload 要求：

- `leadSummary` 是整份简报的总述，不是待办计划；
- `topicClusters` 每组必须引用真实 `contentRef`；
- `recommendationReasons` 解释为什么这些内容被保留；
- `uncertainties` 说明哪些部分仍需用户打开原文确认；
- `leadItem` 可以是 `briefing` 类型，但必须能追溯到来源。

### 2.6 页面展示

页面展示顺序保持：

```text
报头
-> 今日内容摘要
-> 头版重点
-> 关注领域报道
-> 精选热点
-> 速记
-> 对话入口 / 待办线索
```

待办线索可以存在，但不能成为简报页主语。

## 3. 演示 seed

文件：

- `infra/cloudflare/d1/seeds/source/seed.today-briefing-semantic-demo.sql`

本地检查命令：

```bash
npm run db:d1:check-today-demo
```

写入范围：

- `users`：确保 `test@example.com` 的演示用户存在；
- `user_interests`：设置简报筛选关注项；
- `hot_topics`：写入语义稳定的今日内容候选；
- `hot_topic_processing_results`：写入处理后的规范字段；
- `opportunities`：写入少量可转待办线索；
- `briefings`：写入 `2026-05-01` 的简报 payload。

## 4. 本轮验收口径

应用 seed 后，打开 `/today` 应看到：

- 摘要语义像一份简报，而不是待办计划；
- 头版重点围绕“AI 应用进入稳定工作流”；
- 关注领域报道能按 `AI应用`、`远程工作`、`写作素材` 等方向命中；
- 精选热点少量出现，不淹没个人关注；
- 待办线索只作为后段候选；
- 点击内容能带着 `contentRef` 进入 Article 或 Chat。

## 5. 后续数据处理要求

后续真实采集和 AI 加工不要直接以 UI 文案为目标，而应先产出这些中间语义：

```text
source identity
content candidate
normalized content
interest match
briefing rank
AI cluster
page payload
```

如果其中任一层缺失，UI 美化只能遮住问题，不能解决简报页“为什么展示这些内容”的根因。

## 6. 本轮已治理的服务层风险

本轮开始时，`listHotTopics()` 是全库排序：

```text
ORDER BY hot_value DESC, quality_score DESC
LIMIT ?
```

这会导致两个风险：

- 高热但无关的公共热点进入简报；
- 低热但与用户高度相关的新内容被挡在候选集外。

现在已升级为：

```text
用户关注命中
-> 内容质量
-> 热度
-> 发布时间
```

当前仍是轻量治理，后续真实数据处理还应继续升级为：

```text
时间窗口
-> 内容质量
-> 用户关注匹配
-> 公共重要性
-> 去重和来源可信度
```

因此，当前已经可以用演示样板校准简报语义和视觉；但还不能说真实采集、去重、来源可信度和 AI 归并已经完整成熟。
