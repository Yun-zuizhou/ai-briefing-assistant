## 0. 产品 LLM 现状审计

当前产品有两套独立的 LLM 调用链路：

| 链路 | 运行时 | 负责 | 调用方式 |
|------|--------|------|----------|
| **实时链路** | Edge Worker (Cloudflare) | Digest 咨询、即将接入的 Chat 分类/回复 | 直接 fetch LLM API |
| **批处理链路** | Python (FastAPI) | Digest 摘要生成、简报生成、用户画像生成 | `ai_service.py` → `httpx` |

### 各功能 LLM 使用现状

| 功能 | 当前实现 | LLM 状态 | 问题 |
|------|----------|----------|------|
| Chat 意图识别 | `services/chat/intent.ts` 纯规则引擎 | **无** | 覆盖率低，unknown 率高 |
| Chat 回复生成 | `chat.ts` 内硬编码模板函数 | **无** | 生硬，不像对话 |
| Digest 内容摘要 | Python `directed_digest.py` → `ai_service.py` | **有** | Prompt 未标准化 |
| Digest 内容咨询 | `services/content/consult.ts` | **有** | 仅 digest 条目可用 |
| 简报生成 | Python `ai_service.generate_briefing_content()` | **有** | 调用链路不透明 |
| 用户画像分析 | `services/behavior/builder.ts` 纯模板拼接 | **无** | "你是XX探索者，已记录N条..." 千篇一律 |
| 成长关键词 | `builder.ts` 取前 3 个兴趣 + 固定词 | **无** | 无个性化洞察 |
| 期刊摘要 | `builder.ts` 取第一条 note 原文截断 | **无** | 机械，无聚合能力 |
| 建议行动 | `builder.ts` 按优先级排序取前 3 | **无** | 纯规则，无上下文感知 |
| 信息收集打分 | `directed_digest.py` 关键词 + 新鲜度 + 信任权重 | **无** | 关键词匹配粗糙 |

### 核心判断

**LLM 不替代任何现有逻辑。LLM 是"结果增强层"——在现有逻辑之上增加一层智能判断，不可用时无损回退。** 规则引擎、模板拼接、关键词打分永远是降级路径。

## 1. LLM Skill 体系设计

将每个 LLM 增强点封装为独立的 **Skill**——有明确触发条件、Prompt 模板、Token 预算、输出 Schema、校验规则、降级策略。

### 1.1 Skill 总览

```
┌──────────────────────────────────────────────────────────────────┐
│                    LLM Skill 体系                                 │
│                                                                  │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐               │
│  │ 对话类 Skill │  │ 分析类 Skill │  │ 生成类 Skill │               │
│  │ (高频轻量)   │  │ (中频中量)   │  │ (低频重量)   │               │
│  ├─────────────┤  ├─────────────┤  ├─────────────┤               │
│  │ classify    │  │ evaluate    │  │ summarize   │               │
│  │ 意图分类    │  │ 相关性评估   │  │ 内容摘要    │               │
│  │ ~400 tok    │  │ ~500 tok    │  │ ~1500 tok   │               │
│  │ 每次消息    │  │ 模糊区间    │  │ 每天/批次   │               │
│  ├─────────────┤  ├─────────────┤  ├─────────────┤               │
│  │ reply       │  │ analyze     │  │ report      │               │
│  │ 对话回复    │  │ 用户分析    │  │ 周期报告    │               │
│  │ ~200 tok    │  │ (画像+洞察) │  │ ~2500 tok   │               │
│  │ 每次执行后  │  │ ~1500 tok   │  │ 每周/月/年  │               │
│  ├─────────────┤  │ 每周/按需   │  └─────────────┘               │
│  │ multi-turn  │  └─────────────┘                                │
│  │ 多轮上下文  │                                                 │
│  │ 合并到分类  │                                                 │
│  │ (增量token) │                                                 │
│  └─────────────┘                                                 │
│                                                                  │
│  5 个核心 Skill（原 7 个经效果审核合并为 5 个）                    │
│  Skill 6 summarize / Skill 7 report 为已有实现标准化，不列入新建    │
│  所有 Skill 共享同一套 Transport 层（ai-provider.ts 公共函数）     │
│  所有 Skill 共用同一套降级链（LLM → 规则/模板 → 兜底文本）         │
└──────────────────────────────────────────────────────────────────┘
```

### 1.2 Skill 详细规格

#### Skill 1: `classify_intent` — 意图分类 + 实体抽取

| 属性 | 值 |
|------|-----|
| **触发条件** | 每次用户 Chat 消息，规则引擎 `matchedBy ∈ {keyword, fuzzy, fallback}` 或 `matchedBy=pattern ∧ confidence < 0.88`（捕捉 remove_interest 无匹配兴趣词等低置信 pattern 场景） |
| **运行位置** | Edge Worker → `services/chat/llm-classify.ts` |
| **Token 预算** | ~400（system 120 + context 100 + user 150 + output ~100） |
| **温度** | 0.3（分类任务低温，兼顾 replyHint 中文自然度；0.1 会导致回复呆板） |
| **输出 Schema** | `{ type, confidence, entities, candidateIntents, replyHint, suggestedActions }` |
| **校验** | type 必须在已知 9 种意图内；confidence ∈ [0,1]；entities 字段与 type 匹配 |
| **降级** | 返回 null → 调用方使用规则引擎结果 |
| **缓存** | 同一 session 内相同输入 5min 内复用 |

**Prompt 核心结构**：
```
System: 你是意图识别模块。分析用户输入，只返回JSON。
        可用意图：[9种 + 实体格式]
        回复建议：1-2句自然中文确认。当 intent=chat_only 时仍需给出自然回应（如"好的，有需要随时说"）。
        建议操作：1-2个上下文相关的后续建议（如"查看本周AI简报""记下这个想法"）。
        注意：结合对话历史消解指代词。

User:   用户关注：{interests}
        来源：{sourceContext}
        历史：{recentMessages}
        输入：{userInput}
```

**Token 节省技巧**：
- System prompt 中意图列表只用简短格式（`create_todo: {"content":"...","deadline":"..."}`），不用自然语言描述
- entities 字段按需出现（chat_only 不要求 entities）
- replyHint 限制 50 字符
- suggestedActions 每个限制 10 字符，最多 2 个

---

#### Skill 2: `generate_reply` — 对话回复生成（含 chat_only 回应）

| 属性 | 值 |
|------|-----|
| **触发条件** | 每次 Chat 执行完成后（阶段二起）；`chat_only` 意图时生成自然回应 |
| **运行位置** | Edge Worker → `services/chat/llm-classify.ts` |
| **Token 预算** | ~200（system 60 + context 100 + output ~40）；chat_only 场景 ~100 额外 token |
| **温度** | 0.5 |
| **输出 Schema** | 纯文本（1 句，≤35 字）；chat_only 时允许 2-3 句自然回应 |
| **校验** | 长度 ≤ 80 字，非空 |
| **降级** | `buildAssistantReplyText()` 模板；chat_only → "好的，随时找我。" |

**Prompt 核心结构**：
```
System: AI简报助手，风格简洁友善。1句话回复，≤35字，口语化。
        当动作为chat_only时，给一句自然的回应（如"好的，有需要随时说""嗯嗯，我在听"）。

User:   用户说："{input}" | 动作：{action} | 结果：{success/fail}
        详情：{summary}
```

**Token 节省技巧**：
- 这是最简单的 Skill，Prompt 极短
- 不需要 JSON 输出（减少 output token）
- 分类时 `replyHint` 已覆盖大部分确认场景；`generate_reply` 仅在 replyHint 不适用或 chat_only 时独立调用

---

#### Skill 3: `evaluate_relevance` — 信息相关性评估

| 属性 | 值 |
|------|-----|
| **触发条件** | 信息收集 pipeline 中，关键词评分落入模糊区间的内容 |
| **运行位置** | Python（`directed_digest.py` 扩展）或 Edge Worker（新增） |
| **Token 预算** | ~500（system 150 + candidate 250 + interests 50 + output ~100） |
| **温度** | 0.2 |
| **输出 Schema** | `{ score: 0-100, reasons: string[], tags: string[] }` |
| **校验** | score ∈ [0,100]；reasons 非空数组；tags 不重复 |
| **降级** | 关键词评分（当前逻辑） |

**触发策略（成本控制）**：
```
关键词评分结果：
  ≥ 80 分  → 直接收录（高质量信号明确）
  40-80 分 → 调 evaluate_relevance（模糊区间，需要 LLM 判断）
  < 40 分  → 直接丢弃（低质量信号明确）
```

**Prompt 核心结构**：
```
System: 你是信息筛选助手。评估内容与用户兴趣的相关性。
        输出JSON：{ score: 0-100, reasons: ["理由"], tags: ["标签"] }
        评分标准：
        - 90-100：直接相关，应立即推送
        - 70-89：高度相关，可收录
        - 50-69：部分相关，可备选
        - 0-49：不相关，应丢弃

User:   用户兴趣：{interests}
        最近7天互动内容类型：{pastEngagements}
        内容标题：{title}
        内容摘要：{summary}
        来源：{source}（信任度：{trustWeight}）
```
`pastEngagements` 记录用户已读/已收藏/已忽略的内容类型分布，帮助 LLM 区分"用户真正关心的"和"用户一直忽略的"，减少同类误推。

#### Skill 4: `analyze_user` — 用户画像与成长洞察（合并原 4+5）

| 属性 | 值 |
|------|-----|
| **触发条件** | 周报/月报生成时 / 用户查看 My 页面 / 每周自动刷新 / 用户数据发生显著变化（新增 5+ 条记录） |
| **运行位置** | Edge Worker → `services/behavior/` 新增调用 |
| **Token 预算** | ~1500（system 350 + data 600 + output ~400）—— 合并后比独立两次调用省 ~300 token |
| **温度** | 0.5 |
| **输出 Schema** | `{ persona: { summary, keywords: [{word, weight, trend}], traits }, insights: [{title, detail, evidence}], suggestions: string[] }` |
| **校验** | persona.summary 非空 ≥ 10 字；keywords 去重；traits ≥ 2；insights ≥ 1 条且有 evidence；suggestions ≥ 2 条 |
| **降级** | `buildPersonaSummary()` + `buildStatsSummary()` 模板拼接 |
| **缓存** | 24h 内不重复生成，除非数据显著变化 |

**合并理由**：画像和洞察共享同一组输入数据（兴趣、统计、行为历史）、同一触发频率（每周）、且内容互补——画像描述"你是谁"，洞察描述"你变化了什么"。在同一上下文中推理，画像质量更高（LLM 能看到趋势），token 更省（省一次独立调用的 system prompt 开销）。

**Prompt 核心结构**：
```
System: 你是用户画像与成长洞察分析师。基于行为数据生成个性化画像和周期洞察。
        输出JSON：{
          persona: { summary, keywords: [{word, weight, trend}], traits },
          insights: [{title, detail, evidence}],
          suggestions: string[]
        }
        - persona.summary：2-3句自然语言，描述核心特征和变化趋势
        - persona.keywords：成长关键词，含权重(0-100)和趋势(up/down/stable)
        - persona.traits：3-5个行为特征标签
        - insights：2-4条周期洞察，每条有标题、详述、具体数据证据
        - suggestions：2-3条可执行的下一步建议
        要求：基于数据，不编造。数据稀疏时诚实说明。每条洞察必须有数据支撑。

User:   用户兴趣：{interests}
        统计：笔记{n}条，收藏{f}条，待办完成{c}/{t}
        历史行为：{historyCount}条 | 活跃天数：{activeDays}
        周期：{period}（本周/本月）
        本周期新增：笔记{n}条 | 收藏{f}条 | 完成待办{c}项
        兴趣变化：{interestChanges}
        上次画像/洞察：{previousAnalysis}
```

### 1.3 Skill 组合关系

```
用户发送消息
    │
    ├─→ classify_intent (Skill 1)    ← 每次，含 replyHint + suggestedActions
```

## 2. Token 效率策略

### 2.1 分层预算制度

| 层级 | Token/次 | 月调用量（估） | 月Token（估） | 适用 Skill |
|------|----------|---------------|--------------|-----------|
| L1 轻量 | ≤ 400 | ~300 | ~120K | classify, reply |
| L2 中量 | 400-1500 | ~40 | ~45K | evaluate, analyze_user |
| L3 重量 | 1500-2500 | ~30 | ~50K | summarize, report（已有） |

月总预算：~215K tokens（新增约 165K，已有 50K 保持不变）

### 2.2 具体节省手段

| 手段 | 说明 | 节省量 |
|------|------|--------|
| **合并调用** | classify 同时返回 replyHint，省去一次 reply 调用 | ~200 tok/次 |
| **缓存复用** | 相同输入 5min 内复用；画像 24h 缓存 | 视命中率 |
| **分级触发** | evaluate 只在模糊区间调用（约 30% 内容），而非全部 | ~70% evaluate 调用 |
| **Prompt 精简** | System prompt 用缩写格式（`- intent: {field: "desc"}`），不用自然语言段落 | ~30% system prompt |
| **输出限制** | 所有 Skill 设 maxTokens 上限，LLM 不自由发挥 | 防爆 token |
| **上下文截断** | 历史消息只取最近 3-5 轮，每轮截断到 120 字 | ~40% context token |

### 2.3 成本与质量平衡矩阵

```
                        低成本
                          │
            ┌─────────────┼─────────────┐
            │ 规则引擎     │ 轻量LLM     │
            │ (0 tok)     │ classify    │
            │             │ reply       │
            │ 适用：      │ 适用：      │
            │ 明确指令    │ 模糊意图    │
            │ 关键词命中  │ 口语表达    │
            ├─────────────┼─────────────┤
   低质量 ←─│             │             │─→ 高质量
            ├─────────────┼─────────────┤
            │ 关键词打分   │ 中量LLM     │
            │ (0 tok)     │ evaluate    │
            │             │ analyze     │
            │ 适用：      │ (画像+洞察) │
            │ 初筛       │ 适用：      │
            │ 去重       │ 深度分析    │
            │             │ 个性化输出  │
            └─────────────┼─────────────┘
                          │
                        高成本
```

## 3. 质量保证框架

### 3.1 五层防护

```
Layer 1: Prompt Engineering
  └─ 每个 Skill 的 Prompt 经过验证，含明确指令、输出格式、边界约束

Layer 2: Schema Validation
  └─ 所有 Skill（除 reply）强制 JSON 输出，解析后校验字段 + 类型 + 值域

Layer 3: Output Sanitization
  └─ intent 不在已知列表 → 修正为 chat_only
  └─ confidence NaN/负值 → clamp 到 [0.1, 1.0]
  └─ entities 类型错误 → 重置为空对象
  └─ replyHint 为空（含 chat_only） → 生成默认值（"好的，随时找我"）
  └─ suggestedActions 非数组 → 重置为空数组

Layer 4: Dual Confidence
  └─ 规则引擎给 confidence，LLM 也给出 confidence
  └─ 两者差距 > 0.4 时，标记为"争议"，日志记录但不阻断

Layer 5: User Feedback Loop
  └─ reclassify 操作 → 记录 LLM 错误分类
  └─ 连续同类错误 → 标记该 Skill 需 Prompt 调整
```

### 3.2 各 Skill 的校验规则

```
classify_intent:
  ├─ type ∈ {create_todo, record_thought, fragmented_thought,
  │          add_interest, remove_interest, set_push_time,
  │          query_stats, chat_only, multi}
  ├─ confidence ∈ [0, 1]
  ├─ type='multi' → entities.intents 是数组且非空
  ├─ type='chat_only' → entities 为空对象
  └─ replyHint 非空（含 chat_only 自然回应）

evaluate_relevance:
  ├─ score ∈ [0, 100]
  ├─ reasons.length ≥ 1
  └─ tags 每个元素是 string

analyze_user:
  ├─ persona.summary 非空且 ≥ 10 字
  ├─ persona.keywords[].weight ∈ [0, 100]
  ├─ persona.keywords[].trend ∈ {up, down, stable}
  ├─ persona.traits.length ≥ 2
  ├─ insights.length ≥ 1
  └─ insights[].evidence 非空
```

## 4. 架构决策

### 4.1 LLM 调用在哪里完成

**决策：Edge Worker 负责所有实时 LLM 调用，Python 保留批处理 LLM 调用。**

| LLM 调用 | 位置 | 理由 |
|----------|------|------|
| classify_intent | Edge Worker | 实时，Chat SSE 流内，延迟敏感 |
| generate_reply | Edge Worker | 实时，replyHint 覆盖大部分场景 |
| evaluate_relevance | Python | 批处理，pipeline 中非实时 |
| analyze_user（画像+洞察合并） | Edge Worker | 中等频率，可缓存；合并后省一次调用 |
| summarize_content | Python | 批处理，已有实现，标准化收口 |
| generate_report | Python | 批处理，已有实现，标准化收口 |

### 4.2 Transport 层设计

从 `consult.ts` 提取 `chatCompletion()` + `extractText()` 到 `ai-provider.ts`，所有 Skill 共用：

```typescript
// ai-provider.ts
export async function chatCompletion(
  config: ResolvedAiProviderConfig,
  messages: Array<{ role: string; content: string }>,
  options?: { temperature?: number; maxTokens?: number; signal?: AbortSignal }
): Promise<unknown>

export function extractText(config: ResolvedAiProviderConfig, payload: unknown): string
```

### 4.3 Provider 选择

所有 Skill 共用同一套 Provider 选择逻辑：

```

   })
2. resolveEnvSummaryProviderConfig(bindings)（需显式开启）

```

## 6. 关键设计决策

1. **每个 LLM 调用封装为 Skill**：有明确的 Trigger / Prompt / Schema / Budget / Validation / Fallback，确保可复现、可调试、可度量。

2. **合并 classify + reply**：classify 的 `replyHint` 字段覆盖大部分回复场景，省去独立 reply 调用。`generate_reply` 仅在 `replyHint` 不适用（如 chat_only 需更多变化）时调用。

3. **合并 persona + insight → analyze_user**：画像和洞察共享输入、同频触发、内容互补。合并后 LLM 在同一上下文中推理，质量更高，省 ~300 token/次（省一次独立 system prompt）。

4. **evaluate_relevance 留在 Python**：信息收集 pipeline 在 Python 侧运行，LLM 调用也应在同一进程内完成，不跨进程增加延迟。prompt 需携带用户过去 7 天互动内容类型以提升准确性。

5. **缓存优先于调用**：画像 24h 缓存、相同输入 5min 缓存、模糊区间才调 LLM——把调用量压到真正需要的地方。

6. **每阶段有定量验收标准**：阶段不通过不进入下一阶段。阶段一只在 reclassify 下降 40%+ 后才进入阶段二。
