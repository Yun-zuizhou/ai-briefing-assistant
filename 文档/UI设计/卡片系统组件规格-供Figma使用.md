# 卡片系统组件规格 — 供 Figma 设计使用

> 本文档定义 AI简报助手的 7 种卡片信息角色，每种角色的数据结构、视觉规格、状态变体和使用位置。
> 与 DESIGN.md（视觉 tokens）和信息架构说明书（页面内容定义）互补。

---

## 卡片系统的设计原则

1. **卡片角色由"信息意图"决定，不由"所在页面"决定** — 同一个"内容卡片"在简报页和热点页应该外观一致
2. **7 个角色覆盖所有场景** — 不应出现第 8 种角色，现有 40+ 种手写卡片需要收束到 7 个角色
3. **每个角色有固定的信息层级** — 眉标 → 标题 → 摘要 → 元信息/操作区，不允许随意调整
4. **变体只在必要时引入** — 通过 `variant` 控制语义差异（如 `featured` 主稿），不通过 className 手写

## 内容容器密度规则（设计时必须遵守）

**核心问题**：figma 把信息排布逻辑做对了，但缺少"容器感"——文字清晰但散在白纸上，没有通过背景/边框/阴影把信息"框"进可感知的单元。

**解决办法**：每个信息区块在落笔前，先确定它属于哪一级容器密度。不是所有内容都需要可见容器，但该有的必须有。

### 级别 A — 完整容器（background + border + shadow 三者齐全）

**何时使用**：区块是**一个独立可操作的信息单元**。用户可以单独点击它、收藏它、转待办、追问它。它和相邻区块之间是"并列关系"而非"从属关系"。

**视觉要求**：
- `paper-warm` 渐变背景
- 1px `border` 实线边框
- `elevation-card-soft` 阴影（0 6px 14px rgba(44,36,22,0.06)）
- `radius-panel` (10px) 或 `radius-control` (8px) 圆角
- 14px 内边距

**典型场景**：

| 页面 | 哪些区块是 A 级 |
|------|----------------|
| /today | 今日主稿（leadItem）、每条值得知道条目、每条值得行动条目 |
| /chat | 每条消息气泡（用户/助手）、执行结果摘要卡、意图确认卡 |
| /todo | 每条待办项、优先行动卡 |
| /article | 相关推荐条目 |
| /collections | 每条收藏项 |
| /hot-topics | 每条热点话题 |

**反例**：以下区块不要套 A 级容器 —— 整页总述文案、分组标题栏、辅助入口列表、标签组

### 级别 B — 轻容器（仅 background 或仅 border，二选一）

**何时使用**：区块是**一组相关信息的集合**，内部条目之间有逻辑从属关系，但区块本身不作为独立的操作对象。用户不是"点击这个区块"，而是"在这个区块里阅读"。

**视觉要求（两种模式二选一）**：

| 模式 | 适用场景 | 视觉 |
|------|----------|------|
| 仅背景 | 需要让一组内容在视觉上"抱团"，但不强调边界 | `paper-soft` 或 `paper-warm` 浅底色，无边框 |
| 仅分隔线 | 内容本身背景和页面一致，靠底部分隔线划分 | 无底色，仅 `border-bottom` 虚线分隔 |

**典型场景**：

| 页面 | 哪些区块是 B 级 | 用哪种模式 |
|------|----------------|-----------|
| /today | AI简报区（topicClusters 的容器） | 仅背景 |
| /today | 关注推荐分组（每个 interestName 下的一组 topItems） | 仅分隔线 |
| /growth | 关键词标签区 | 仅背景 |
| /growth | 本周总述 | 仅背景 |
| /profile | 画像维度区块 | 仅背景 |
| /reports | 话题趋势分组 | 仅背景 |
| /me | 入口分组（"系统设置"/"支持"） | 仅分隔线 |

**反例**：不要给 B 级加阴影，不要加完整四边边框

### 级别 C — 无容器（纯文本流）

**何时使用**：内容是**连续的编辑性叙事**，不需要视觉边界来区分"这一块"和"那一块"。层级由排版（字号/字重/间距/缩进）来传达，不由容器来传达。

**视觉要求**：
- 无背景色（透明）
- 无边框
- 无阴影
- 依靠标题、正文、元信息的字号/字重/间距安排阅读节奏

**典型场景**：

| 页面 | 哪些区块是 C 级 |
|------|----------------|
| /today | 今日总述（summary.summaryText）、报头信息 |
| /growth | 人格画像描述文本 |
| /reports | LLM 趋势解读段落、年度总结寄语 |
| /article | 正文内容区 |
| /profile | 画像描述文本 |

**关键约束**：C 级中如果出现"一句话 + 一个按钮"的组合，检查是否应该升级为 B 级（仅背景）。如果用户需要对这个内容采取操作，它就不是纯阅读流。

### 三级密度速查表

| 级别 | 背景 | 边框 | 阴影 | 圆角 | 何时用 |
|------|------|------|------|------|--------|
| A | paper-warm 渐变 | 1px solid | soft | 8-10px | 独立可操作单元 |
| B | paper-soft（可选） | 仅虚线底边（可选） | 无 | 无或 8px | 信息集合/分组容器 |
| C | 透明 | 无 | 无 | 无 | 纯编辑性叙事 |

### 设计检查清单

每个页面设计完成后，检查以下问题：

1. 用 A 级容器的区块，能不能独立点击/操作？不能 → 降为 B 级
2. 用 B 级容器的区块，内部是不是至少 2 条相关内容？不是 → 考虑降为 C 级或升为 A 级
3. 用 C 级的连续文本，有没有超过 5 行？超过了 → 检查是否需要加轻容器防止视觉疲劳
4. A 级容器之间有没有留够间距（≥12px）？没有 → 视觉上会粘连
5. B 级轻容器内部，条目的视觉层级是否小于 A 级？不是 → 用户会分不清哪个能点、哪个不能点

## 角色 1：内容卡片 ContentCard

### 信息意图
承载**一条可独立消费的信息**。用户通过阅读这张卡片来判断是否值得进一步查看详情。

### 数据结构

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `eyebrow` | string | 是 | 眉标：来源名称 / 兴趣领域 / 内容类型（如"值得知道"、"科技动态"） |
| `title` | string | 是 | 主标题，1-2行，超长截断 |
| `summary` | string | 否 | 摘要，2-4行，超长截断 |
| `meta` | { source, time } | 否 | 来源名称 + 时间 |
| `tags` | string[] | 否 | 标签列表（如"AI"、"开源"） |
| `featured` | boolean | 否 | 是否主稿（视觉权重最高） |
| `onClick` | function | 否 | 点击跳转详情 |

### 信息层级（从上到下）

```
┌─────────────────────────────────────┐
│ 眉标（11px, accent/gold, 加粗）      │  ← eyebrow
│ 主标题（16px, ink, 加粗, 1-2行）     │  ← title
│ 摘要（12px, ink-muted, 2-4行）       │  ← summary
│ ─────────────────────────────────── │
│ 标签组（可选）+ 来源·时间（11px）     │  ← tags + meta
└─────────────────────────────────────┘
```

### 视觉规格

| 属性 | 默认 | featured（主稿） |
|------|------|-------------------|
| 背景 | `paper-warm` 渐变 | `paper-warm` 渐变 + 金色径向光晕 |
| 边框 | 1px `border` | 1px `border` + 左侧 3px `gold` |
| 圆角 | `radius-control` (8px) | `radius-panel` (10px) |
| 内边距 | 14px | 16px |
| 阴影 | `elevation-card-soft` | `elevation-card-mid` |
| 眉标装饰线 | 虚线（顶部） | 虚线 + 金色菱形符号 |

### 使用位置

| 页面 | 具体场景 |
|------|----------|
| /today | 值得知道条目、关注推荐条目 |
| /hot-topics | 热点话题列表项 |
| /collections | 收藏条目 |
| /article | 相关推荐条目 |
| /history-brief | 历史简报条目 |

### 状态

| 状态 | 说明 |
|------|------|
| 默认 | 正常可交互 |
| hover/active | 背景加深 `paper-warm` → `paper-dark`，左移 1px |
| featured | 主稿模式，视觉权重最高 |

## 角色 2：行动卡片 ActionCard

### 信息意图
促使用户**采取一个明确的行动**。卡片告诉用户"有一件事值得你做"、"截止什么时候"、"怎么做第一步"。

### 数据结构

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `actionType` | enum | 是 | `apply` / `follow` / `submit` / `read_later` / `create_todo` |
| `title` | string | 是 | 行动标题 |
| `summary` | string | 是 | 为什么这件事值得你做 |
| `deadline` | string | 否 | 截止日期 |
| `reward` | string | 否 | 回报说明 |
| `difficulty` | enum | 否 | `low` / `medium` / `high` |
| `primaryActionLabel` | string | 是 | 主动作按钮文案（如"查看详情"、"转为待办"） |
| `onPrimaryAction` | function | 是 | 主动作回调 |
| `secondaryActionLabel` | string | 否 | 次动作按钮文案 |
| `onSecondaryAction` | function | 否 | 次动作回调 |

### 信息层级

```
┌─────────────────────────────────────┐
│ 行动类型标签（accent 底色）          │  ← actionType chip
│ 行动标题（15px, ink, 加粗）          │  ← title
│ 为什么值得做（13px, ink, 1-2行）     │  ← summary
│ ─────────────────────────────────── │
│ 截止日 + 难度 + 回报（11px, muted）  │  ← meta 行
│ ─────────────────────────────────── │
│ [主动作按钮]  [次动作]              │  ← actions
└─────────────────────────────────────┘
```

### 视觉规格

| 属性 | 值 |
|------|-----|
| 背景 | `paper-warm` 渐变 |
| 边框 | 1px `border` |
| 圆角 | `radius-control` (8px) |
| 内边距 | 14px |
| 行动类型标签 | accent 渐变背景，白色文字，6px 圆角 |
| 主动作按钮 | `button-primary`（朱红色） |
| 次动作按钮 | `button-soft` |

### 使用位置

| 页面 | 具体场景 |
|------|----------|
| /today | 值得行动的（worthActing[]） |
| /todo | 待办项、优先行动、建议下一步 |
| /article | 文章中的机会卡片（article opportunity card） |

### 状态

| 状态 | 说明 |
|------|------|
| 默认 | 待行动 |
| 进行中 | actionType label 变为 "进行中"，金底 |
| 已完成 | 整体灰化，opacity 0.6，主按钮变为 "已完成" |
| 已过期 | deadline 红字，卡片边框 accent |

## 角色 3：摘要卡片 SummaryCard

### 信息意图
概括**一段交互的结果或一个话题簇的全貌**。用户读到这张卡片是为了快速了解"发生了什么"、"结果是什么"。

### 数据结构

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `icon` | enum | 是 | 图标名（briefing / bell / bookmark / star） |
| `title` | string | 是 | 摘要标题（如"本轮摘要"、"AI 简报"） |
| `badgeLabel` | string | 否 | 状态标签（如"已执行"、"成功"） |
| `badgeTone` | enum | 否 | `pending` / `success` / `neutral` |
| `leadText` | string | 是 | 一句话结果/引语 |
| `detailText` | string | 否 | 详细说明 |
| `metaNote` | string | 否 | 底部小字说明（如"具体结果在下方消息中"） |
| `primaryAction` | { label, onClick } | 否 | 主动作（如"查看结果"） |
| `sourceRefs` | { title, sourceLabel }[] | 否 | 引用的来源列表（AI简报用） |

### 信息层级

```
┌─────────────────────────────────────┐
│ ◆ 摘要标题  [状态标签]              │  ← icon + title + badge
│ ─────────────────────────────────── │  ← 虚线分隔
│ 意图分类标签（如"记录想法"）        │  ← 可选
│                                     │
│ 一句话结果（14px, ink, 加粗）       │  ← leadText
│ 详细说明（13px, ink-light）          │  ← detailText
│ 引用来列表（如AI简报用）            │  ← sourceRefs
│ ─────────────────────────────────── │
│ 底部小字（11px, muted）             │  ← metaNote
│ [查看结果按钮]                     │  ← primaryAction
└─────────────────────────────────────┘
```

### 视觉规格

| 属性 | 默认 | pending（待确认） |
|------|------|-------------------|
| 背景 | `chat-bubble-assistant` 渐变 | 略暗，表示未完成 |
| 边框 | 1px `bookish-border` | 1px `gold`（虚线） |
| 圆角 | `radius-control` (8px) | 同 |
| 内边距 | 12px | 同 |
| 图标 | `EditorialIcon` 18px | 同 |
| 来源引用 | 浅底描边小条 | 同 |

### 使用位置

| 页面 | 具体场景 |
|------|----------|
| /chat | 对话执行结果（ResultSummaryCard）、意图确认（PendingConfirmationCard）、动作上下文（ActionContextCard） |
| /today | AI 简报簇（TodayAiBriefingCluster） |

### 状态

| 状态 | 说明 |
|------|------|
| 成功 | badge "已执行"（success 色），完整结果显示 |
| 待确认 | badge "待确认"（pending 色），候选意图列表 |
| 上下文 | badge "已带入"，来源内容显示 |
| 降级 | badge "基于规则"，无 confidence 显示 |

## 角色 4：统计卡片 MetricCard

### 信息意图
展示**一个数值型指标**。用户扫读即可获取量化信息，不需要深入阅读。

### 数据结构

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `value` | string \| number | 是 | 主数值（如"47"、"12天"） |
| `label` | string | 是 | 数值说明（如"查看内容"、"连续签到"） |
| `accent` | boolean | 否 | 是否突出（数字变 accent 色） |
| `trend` | enum | 否 | `up` / `down` / `stable` — 趋势箭头 |
| `comparison` | string | 否 | 对比文本（如"较上周 +3"） |

### 信息层级

```
┌───────────────────────┐
│                       │
│   47                 │  ← value（20px, 加粗 900）
│   查看内容           │  ← label（11px, muted）
│   较上周 +3 ↑        │  ← comparison（11px, gold/green）
│                       │
└───────────────────────┘
```

### 视觉规格

| 属性 | 默认 | accent |
|------|------|--------|
| 背景 | `paper-warm` 渐变 | 同 |
| 边框 | 1px `border` | 同 |
| 圆角 | `radius-control - 2px` | 同 |
| 内边距 | 10px | 同 |
| 数值颜色 | `ink` | `accent` |
| 顶部装饰 | 虚线（金色） | 同 |

### 使用位置

| 页面 | 具体场景 |
|------|----------|
| /growth | 查看数、记录数、收藏数、完成数 |
| /todo | 签到天数 |
| /me | 账号统计 |
| /reports | 报告总览数字（overview stats） |
| /journal | 表达次数、进展项数、沉淀项数 |

### 状态

| 状态 | 说明 |
|------|------|
| 默认 | 正常显示 |
| 上升趋势 | 数值后 ↑（gold） |
| 下降趋势 | 数值后 ↓（accent） |
| 无数据 | 显示 "—" + label |

## 角色 5：入口卡片 NavigationCard

### 信息意图
引导用户**导航到另一个页面或功能区**。卡片本身不作为信息终点，而是一个"门"。

### 数据结构

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `title` | string | 是 | 目标页面/功能名称 |
| `description` | string | 是 | 一句话说明要去做什么 |
| `icon` | string | 否 | 前置图标 |
| `onClick` | function | 是 | 导航回调 |
| `trailing` | ReactNode | 否 | 尾部装饰（默认右箭头） |

### 信息层级

```
┌─────────────────────────────────────┐
│ ◆ 设置  →                          │  ← title + trailing
│ 查看对话配置结果、提醒摘要和基础偏好 │  ← description
└─────────────────────────────────────┘
```

### 视觉规格

| 属性 | 值 |
|------|-----|
| 背景 | `domain-card` 标准渐变 |
| 边框 | 1px `border` |
| 圆角 | `radius-panel` (10px) |
| 内边距 | 12px 18px |
| 标题 | 15px, 加粗, `ink` |
| 描述 | 12px, `ink-muted` |
| 尾部箭头 | `ChevronRight` 18px, `ink-muted` |
| hover | 背景加深，箭头变 `accent` |

### 使用位置

| 页面 | 具体场景 |
|------|----------|
| /me | 设置入口、AI服务设置入口、通知偏好入口、帮助反馈入口、关于入口 |
| /growth | 周报/月报/年报入口 |
| /settings | 子设置入口（如果在设置页内分组） |

### 状态

| 状态 | 说明 |
|------|------|
| 默认 | 正常可导航 |
| hover | 背景加深 |
| disabled | 灰色，不可点击（如报告不可用） |

## 角色 6：状态卡片 StateCard

### 信息意图
告知用户**系统或流程的当前状态**——不是信息也不是行动，而是一种"情况说明"。这是 7 种角色中使用频率最高、但当前最分散的一种。

### 数据结构

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `state` | enum | 是 | `loading` / `empty` / `error` / `partial` / `fallback` |
| `icon` | string | 否 | 状态图标（默认按 state 自动匹配） |
| `title` | string | 是 | 状态标题 |
| `description` | string | 否 | 状态说明 |
| `actionLabel` | string | 否 | 操作按钮文案（如"重试"、"更新关注"） |
| `onAction` | function | 否 | 操作回调 |
| `reason` | string | 否 | 技术原因（仅 error/partial 态，display:none 对用户） |

### 信息层级（按 state 不同）

```
空内容态：
┌──────────────────────────────────────┐
│                                      │
│         [图标 80px]                  │
│        你还没有待办事项               │  ← title（17px, 加粗）
│   从简报中把值得行动的内容转为待办    │  ← description（14px, muted）
│         [开始设置关注]               │  ← action（可选）
│                                      │
└──────────────────────────────────────┘

错误态：
┌──────────────────────────────────────┐
│   ⚠ 数据加载失败                     │  ← title（15px, accent）
│   网络连接异常，请检查后重试          │  ← description
│   [重试]                             │  ← action
└──────────────────────────────────────┘

加载态：
┌──────────────────────────────────────┐
│                                      │
│         [旋转图标 60px]              │
│         正在加载...                  │  ← title（14px, muted）
│                                      │
└──────────────────────────────────────┘
```

### 视觉规格

| 状态 | 背景 | 图标色 | 标题色 | 说明 |
|------|------|--------|--------|------|
| loading | `paper-soft` + 金色渐变 | `gold` | `ink-muted` | 居中，垂直排列 |

## 给 Figma 的设计指令

1. **这 7 种角色是排他的** — 不要在第 7 种之外再创造新的卡片类型。如果某个场景无法套入 7 种角色，说明信息架构有问题，不是卡片不够。

2. **每种角色先设计 default + 1 个变体** — ContentCard 做 default + featured，ActionCard 做 default + 已完成，StateCard 做 empty + error，依次类推。其他变体可以由这两个推导。

3. **卡片之间的一致性比个性更重要** — 所有卡片的圆角、内边距、边框色、阴影必须从 `design-md/DESIGN.md` 的 tokens 中取值。不要为某一种卡片单独调整圆角或阴影。

4. **卡片内容用真实数据填充** — 参考信息架构说明书中每个页面的数据结构字段。不要填 Lorem ipsum。

5. **先设计 ContentCard 和 StateCard** — 这两种覆盖了最多的使用场景。ContentCard 的骨架（眉标→标题→摘要→元信息）会被 ActionCard 和 SummaryCard 复用。StateCard 规范好后，全站 20+ 处手写状态卡片就有统一模板。

# 第二部分：AI 对话意图识别交互规格

> 本文档定义 AI 对话页面中，**用户输入一句话后，系统如何理解意图、如何与用户交互确认、如何给出可操作反馈** 的完整交互流程。
> 这是当前项目中最核心但定义最分散的功能——逻辑散落在 6+ 个文件中。本文档从代码中提取事实，整理为 Figma 可直接使用的交互规格。

---

## 1. 意图识别概览

### 什么是"意图"

用户在对话中输入自然语言（如"提醒我明天交报告"），系统识别这句话想做什么——是创建待办？记录想法？调整关注？还是纯聊天？

### 系统能识别 9 种意图

| 意图类型 | 中文标签 | 含义 | 示例用户输入 |
|----------|----------|------|-------------|
| `create_todo` | 记成待办 | 创建待办事项 | "提醒我明天交报告"、"下周要面试" |
| `record_thought` | 记成记录 | 记录一条想法 | "记下：今天读到一篇好文章" |
| `fragmented_thought` | 记成碎片 | 记录碎片想法 | "突然想到一个点子"、"灵感来了" |
| `chat_only` | 仅聊天 | 纯对话，不保存 | "今天天气怎么样" |
| `add_interest` | 更新关注 | 添加关注领域 | "帮我关注AI"、"想看产品设计" |
| `remove_interest` | 移除关注 | 取消关注 | "不想再看娱乐八卦" |
| `set_push_time` | 调整推送时间 | 修改推送时间 | "每天8点推送" |
| `query_stats` | 查看数据 | 查询个人统计 | "这周看了多少" |
| `reclassify` | 手动重分类 | 用户手动修正意图 | （用户点击按钮触发，非自然输入） |

### 识别方式

- **关键词匹配**（`intent.ts`）：对常见词和句式做模式匹配，如"提醒我"→待办、"不想看"→移除关注
- **LLM 分类**（`llm-classify.ts`）：关键词不确定时调用 LLM 判断
- **用户手动指定**（`ModeChips`）：用户通过模式按钮主动选择意图

## 3. 每个交互组件的详细规格

### 3.1 用户消息气泡

**何时出现**：用户每次发送消息后

**视觉**：
- 朱红底色（`accent` #A63D2F）
- 白色文字（`paper` #F5F2E8）
- 圆角 8px
- 右对齐（`editorial-chat-row--user`）
- 最大宽度 min(318px, 88%)

**状态**：
- 发送中：气泡右侧显示 loading 动画
- 已识别：气泡正常显示，无额外标记

### 3.2 助手消息气泡（含简报头）

**何时出现**：系统每次回复消息后

**视觉**：
- 暖纸底色（`paper-warm` + 渐变）
- 圆角 8px
- 左对齐
- 顶部有"简报头"：图标 + 标签 + 状态徽标 + 时间

**简报头内容**（根据 `messageState` 变化）：

| messageState | 图标 | 标签 | 徽标 |
|-------------|------|------|------|
| `executed` | briefing | 本轮简报 | 已执行 (success) |
| `error` | bell | 系统 | 失败 (neutral) |
| `pending_confirmation` | bell | 处理中 | 处理中 (pending) |

**气泡底部元素**（仅在 assistant 消息中显示）：
- 引用原文（用户原始消息的小字回显）
- "为什么这样理解？" — 可折叠的意图分析说明
- 可操作按钮行（deepLink 跳转 + quickActions 纠正按钮）
- 变更日志（如"创建了待办 #42"）
- 操作行：复制 / 重新生成 / 删除

### 3.3 PendingConfirmationCard — 意图确认卡片

**何时出现**：系统识别到意图但需要用户确认时。触发条件：
- 置信度 < 0.9 且候选意图 > 1 个，或
- 意图涉及系统配置（add_interest / remove_interest / set_push_time）

**卡片结构**：

```
┌─────────────────────────────────────────┐
│ 请你确认                    [待确认]     │  ← 标题 + 状态徽标
│ ─────────────────────────────────────── │
│ 候选 2 个          涉及系统配置          │  ← 元信息行
│ ─────────────────────────────────────── │
│                                         │
│ ┌─────────────────────────────────┐     │
│ │ "提醒我明天交报告"               │     │  ← 用户原文引用
│ └─────────────────────────────────┘     │
│                                         │
│ 这会修改你的系统配置。确认后才会写入…     │  ← 仅涉及系统配置时显示
│ ─────────────────────────────────────── │
│ [记成待办] [记成记录] [仅聊天，不保存]    │  ← 候选意图按钮
└─────────────────────────────────────────┘
```

**候选意图按钮规则**：
- 每个 `candidateIntents[]` 中的意图渲染为一个 `PaperButton`
- 额外追加"仅聊天，不保存"按钮
- 系统当前识别到的意图高亮（`active` 状态）
- 涉及系统配置时显示警告文案

### 3.4 ResultSummaryCard — 执行结果摘要卡片

**何时出现**：系统执行操作成功后

**卡片结构**：

```
┌─────────────────────────────────────────┐
│ ◆ 本轮简报                    [已执行]   │  ← 图标 + 标签 + 徽标
│ ─────────────────────────────────────── │
│ 记成待办                                 │  ← 确认的意图类型（中文）
│                                         │
│ 已为你创建待办：明天交报告                │  ← 成功消息（加粗）
│ 已创建待办「明天交报告」                   │  ← 结果摘要（正文）
│                                         │
│ 具体结果和可继续动作都在下面的消息里…       │  ← 说明小字
│ ─────────────────────────────────────── │
│ [查看待办]                               │  ← deepLink 跳转按钮
│                                         │
│ [改记成记录] [改记成碎片] [仅聊天]         │  ← 纠正按钮
└─────────────────────────────────────────┘
```

**可操作按钮生成规则**（`buildCorrectionQuickActions`）：

当前系统识别的意图如果是 `create_todo` / `record_thought` / `fragmented_thought` / `chat_only` 之一，自动生成**纠正按钮**——列出除当前意图外的其他 3 种选项：

```
当前意图        生成的纠正按钮
────────        ──────────────
记成待办    →   改记成记录 / 改记成碎片 / 改记成仅聊天
记成记录    →   改记成待办 / 改记成碎片 / 改记成仅聊天
记成碎片    →   改记成待办 / 改记成记录 / 改记成仅聊天
仅聊天      →   改记成待办 / 改记成记录 / 改记成碎片
```

**deepLink 跳转按钮**（`nextPageLabel` + `deepLink`）：仅当 `deepLink` 和 `nextPageLabel` 同时存在时显示。

### 3.5 ChatInputArea — 输入区

**结构**（从上到下）：
```
┌─────────────────────────────────────────┐
│ 当前模式    涉及写入时，我会先确认，再执行  │  ← 模式说明行
│                                         │
│ [智能] [待办] [想法]  │  [碎片] [聊天]    │  ← 模式切换按钮（两行）
│                                         │
│ 🔍 │ 直接说出关注、任务、想法或调整…  │ ➤ │  ← 输入栏
└─────────────────────────────────────────┘
```

**5 种模式**（`ComposeMode`）：

| 模式 | 标签 | 含义 | placeholder |
|------|------|------|-------------|
| `smart` | 智能 | 自动判断意图 | "直接说出关注、任务、想法或调整..." |
| `create_todo` | 待办 | 强制转为待办 | "直接说出关注、任务、想法或调整..." |
| `record_thought` | 想法 | 强制转为记录 | "直接说出关注、任务、想法或调整..." |
| `fragmented_thought` | 碎片 | 强制转为碎片 | "更适合碎片想法，确认后再决定是否落库" |
| `chat_only` | 聊天 | 仅聊天不保存 | "这次只聊天，不保存内容..." |

**模式说明行**：根据当前模式显示不同提示文案。

### 3.6 快捷操作按钮规则

执行成功后，助手消息气泡底部会出现可操作按钮，生成规则：

**规则 1 — deepLink 跳转按钮**：
- 条件：`deepLink` 存在 且 `nextPageLabel` 存在
- 显示：一个 `PaperButton`，label 为 `nextPageLabel`，点击跳转 `deepLink`
- 常见示例：执行了 create_todo → 显示"查看待办"按钮 → 跳转 `/todo`

**规则 2 — 纠正按钮**：
- 条件：当前意图是 create_todo / record_thought / fragmented_thought / chat_only 之一
- 显示：当前意图之外的其他 3 种，每个一个 `PaperButton`
- 注意：修正按钮始终显示（`changeLog` 不影响按钮生成）

**规则 3 — 来自"文章追问"的标记**：
- 条件：`sourceContext === 'article_action'`
- 显示：在"为什么这样理解？"中显示"这条消息来自你正在看的文章。"

## 4. 设计时需要展示的关键交互状态

### 4.1 用户消息状态

| 状态 | 视觉 | 触发条件 |
|------|------|----------|
| 发送中 | 气泡 + 右侧 loading 动画 | 正在等待服务器响应 |
| 已识别 | 正常气泡 | 服务器已识别意图 |
| 识别失败 | 正常气泡 + 红色感叹号 | 网络错误 |

### 4.2 助手消息状态（7 种 `ChatMessageState`）

| 状态 | 简报头 | 气泡样式 | 底部元素 |
|------|--------|----------|----------|
| `sending` | 无简报头 | 暖纸气泡 | loading 动画 |
| `recognized` | ◆ 系统 | 暖纸气泡 | "为什么这样理解？" |
| `pending_confirmation` | ◆ 处理中 [处理中] | pending 变体（稍暗背景） | PendingConfirmationCard |
| `confirmation` | ◆ 处理中 [处理中] | 暖纸气泡 | — |
| `executed` | ◆ 本轮简报 [已执行] | 暖纸气泡 | 操作按钮 + 变更日志 + 复制/重新生成/删除 |
| `error` | ◆ 系统 [失败] | 暖纸气泡 | 错误信息 + 重试 |

### 4.3 空会话态

对话页首次进入（无历史消息）时：
- 编辑报头
- HeroCard：产品简介 + 模式说明 + 输入框
- 无消息列表

### 4.4 历史会话切换

- 侧栏 SessionList：每个会话项显示标题 + 状态 + 消息数 + 最后活动时间
- 切换会话时：消息列表替换为选中会话的消息

---

## 5. 给 Figma 的设计指令

1. **先理解完整流程再看组件** — 以上 5 个阶段（发送→分析→确认/执行→展示）是对话页的核心骨架。设计时先确保这个流程完整可走通，再调整每个组件的视觉。

2. **可操作按钮是核心体验** — 执行后的"纠正按钮"（改记成XX）是用户最频繁使用的交互。这些按钮的视觉权重不能太低——它们不是"Footer Notes"，而是对话页的第二核心功能区。

3. **PendingConfirmationCard 和 ResultSummaryCard 必须差异化** — 前者是"等待用户决策"，后者是"告知用户结果"。两者的视觉差异必须足够大，用户一眼就知道哪个需要点击、哪个是信息。

4. **模式切换（ModeChips）是轻量操作** — 这是一个辅助功能，不应抢占输入区的视觉焦点。模式按钮用 PaperButton 的默认样式，选中的高亮即可。

5. **deepLink 跳转按钮需要明确的目标感** — "查看待办"这样的按钮应该让用户知道点击后会离开对话页。可以用一个 subtle 的外链图标或不同的按钮色调来提示。

6. **所有按钮文案使用 `intentLabels.ts` 中的中文标签** — 不要自创说法。"记成待办"不是"创建待办"，"记成记录"不是"保存想法"，这些词是产品语言的一部分。

---

# 第三部分：行动建议交互 v2 设计约束

> 本文档定义对话页"行动建议"区域的 v2 升级边界：**从系统枚举式标签升级为 LLM 实时生成的针对性行为推荐**。
> 边界内可以任意改，边界外不许动。figma 设计 + 后续代码更新都在此约束内进行。

---

## 1. 当前问题

**v1（代码现状）**：按钮文案是系统枚举标签 —— "记成待办"、"记成记录"、"记成碎片"、"仅聊天"。用户在代码返回的结果里选一个系统分类。

**figma 已经做出的更好方向**：对话结果 + 行动引导放在一起，用"接下来你可以"的句式，引导用户做有意义的下一步。

**但还不够**："接下来你可以深入了解 Claude Code" 仍然是通用行为推荐，没有结合用户的具体上下文做针对性建议。

---

## 2. v2 目标

**从"菜单式建议"升级为"编辑式推荐"**。

| | v1（现状） | v2（目标） |
|---|-----------|-----------|
| 文案来源 | 后端枚举查表 | LLM 根据用户输入上下文实时生成 |
| 文案语气 | 系统分类标签 | 结合用户刚才说的话，给具体的行动建议 |
| 示例 | "记成待办" | "Claude Code 今天刚发布，要不要先收藏这篇报道？" |
| 用户感知 | "系统在让我选一个分类" | "助手在帮我想接下来该怎么做" |

---

## 3. 改动的边界（不可越界）

### 3.1 行动类型枚举不变（后端固定）

用户能做的始终是这 4 大类 + 1 个降级：

| 行动类型 | 含义 | 后端操作 |
|----------|------|----------|
| `ask_followup` | 继续追问这个话题 | 进入新一轮对话，不写入任何存储 |
| `save_note` | 记一笔自己的想法 | 写入 note（取代 record_thought / fragmented_thought） |
| `add_todo` | 加入待办，稍后处理 | 写入 todo |
| `save_favorite` | 加入收藏，方便回看 | 写入 favorite |
| `chat_only` | 仅聊天，不保存 | 无写入（降级态） |

**这 5 种是永远固定的**。LLM 只能在这 5 种里选，不能发明新的。

### 3.2 建议数量有上限（后端固定）

每次对话回复后，行动建议 **2-3 条**。不能超过 3 条。

### 3.3 按钮结构不变（前端固定）

- 按钮始终是 `PaperButton` 组件
- 排列方式由设计决定（可分组，如"立刻做" / "稍后做"），但组件本身不变
- 跳转按钮（deepLink）和行动建议按钮是两种视觉层级

---

## 4. 改动的自由区（边界内可以任意改）

### 4.1 文案生成（LLM 自由区）

每条行动建议的 **具体文案** 由 LLM 根据上下文实时生成。后台会给 LLM 提供：

- 用户刚才说了什么
- 系统识别到了什么意图
- 当前有哪些内容引用（如果有 sourceTitle / sourceUrl）
- 用户的关注领域

LLM 生成文案的**语气指引**（写在 prompt 里，不是代码逻辑）：

```
你是用户的简报助手。用户刚问了一句话，系统已经做了处理。
现在请你给用户 2-3 条"接下来可以做什么"的建议。

每条建议必须：
- 用口语化、有针对性的语气（不是菜单标签）
- 结合用户刚才说的具体内容（不是泛泛的"查看详情"）
- 让用户感觉你在帮他想，不是在让他选菜单

错误示范："查看详情"、"添加到待办"
正确示范："Claude Code 今天刚发布——要不要先收藏这篇报道？"
          "AI 法案影响面很大，我可以帮你梳理一个跟进清单"
```

### 4.2 按钮分组（设计自由区）

按钮可以按"立刻 / 稍后 / 保存"分组排列。具体分组方式由设计决定，代码只负责渲染。

**推荐的语义映射**：

| 分组 | 包含的行动类型 | 含义 |
|------|---------------|------|
| 立刻追问 | `ask_followup` | 继续对话，深入了解 |
| 记下来 | `save_note` | 记录自己的想法和思考 |
| 稍后处理 | `add_todo` | 加入待办，设提醒跟进 |
| 保存备查 | `save_favorite` | 收藏内容，方便以后回看 |

### 4.3 优先级排序（LLM 自由区）

哪条建议排第一、哪条排第二，由 LLM 根据上下文决定。比如：
- 刚发布的重大新闻 → 收藏排第一，追问排第二
- 用户说"最近想学前端" → 待办排第一（设学习计划），追问排第二

---

## 5. 与 v1 的兼容过渡

v1 的 9 种意图类型和 v2 的 5 种行动类型的映射：

| v1 意图类型 | v2 行动类型 | 说明 |
|-------------|-----------|------|
| `create_todo` | `add_todo` | 合并，待办 |
| `record_thought` | `save_note` | 合并，记想法 |
| `fragmented_thought` | `save_note` | 合并，碎片也是记想法 |
| `chat_only` | `chat_only` | 不变 |
| `add_interest` | 内部操作 | 不生成行动建议，直接写入配置 |
| `remove_interest` | 内部操作 | 同上 |
| `set_push_time` | 内部操作 | 同上 |
| `query_stats` | 内部操作 | 同上 |
| `reclassify` | — | 废弃，v2 不需要此操作 |

**过渡策略**：后端先保留 9 种意图的识别逻辑不变，在生成行动建议的环节（`buildSuggestedActions`）切换为 LLM 生成文案。内部操作（add/remove interest、set_push_time、query_stats）不生成行动建议按钮。

---

## 6. 给 Figma 的设计指令

1. **行动建议不要用系统标签** — 不要写"添加待办"、"保存笔记"这种菜单式文案。每一条建议应该读起来像是助手根据用户刚才说的话，给出的针对性提议。

2. **2-3 条建议，不能多** — 超过 3 条用户就不看了。宁可少而精准，不要多而泛。

3. **按钮可以分组但不要超过 3 组** — 推荐分组：立刻追问 / 记下来 / 稍后或保存。具体视觉排列由你决定。

4. **deepLink 跳转按钮与行动建议按钮是两种视觉层级** — "查看待办"这样的跳转是系统告知型按钮，LLM 生成的行动建议是推荐型按钮。两者放在一起但要能区分。

5. **设计示例文案时，假定用户刚问了一个具体问题** — 不要用"查看详情"这种泛文案。用具体的示例：用户问了科技新闻 → 建议"Claude Code 刚发布，要不要收藏这篇报道？"
